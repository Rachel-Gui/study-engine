## Central question

How do you turn a probability into a decision, and where does human review belong?

:::narration
Classification predicts a category rather than a number. But the model does not
actually hand you a category. It hands you a probability, and somebody has to choose
the cut point that turns that probability into an action. That choice is not
statistical, it is a judgement about which mistake you can least afford. That is what
this episode is really about.
:::

## What is classification?

:::glossarynote
:::

Classification predicts a category: which of a fixed set of labels a case belongs to,
based on its {{features}}. Before picking an algorithm, define five things:

:::workflow
The decision | What action will the prediction inform? | 
The prediction unit | One building, one facade image, one room, one sensor event? | 
The features | What is actually available at prediction time, not in hindsight. | 
The target label | The labelling rule, written down, so two people would agree. | 
The evaluation context | The building types, seasons, and conditions the model will actually meet. | 
:::

:::cards
Binary | Two possible classes | Review now / monitor
Multiclass | One of several classes | Brick / glass / concrete / metal
Multilabel | Several labels at once | Door + window + desk
Ordinal | Classes with an order | Good / fair / poor / critical
:::

:::keyidea
Don't force a continuous quantity into arbitrary categories when the original number
would serve better. Predict annual energy use with {{regression}} unless the decision
genuinely needs a documented performance band.
:::

## Probabilities, decisions, and thresholds

A binary classifier returns a score between 0 and 1. The score becomes a class
decision only after a threshold is selected.

- Lowering the threshold identifies more true cases but creates more false alarms.
- Raising it reduces false alarms but misses more true cases.
- **0.50 is a convention, not a universal optimum.**
- The threshold should reflect the relative consequences of false negatives and false
  positives, the available review capacity, and probability calibration.

:::compare
False positive | Called fine — actually isn't | Ships into a built, occupied building. Expensive, sometimes impossible, to fix afterwards.
False negative | Called a problem — actually fine | Costs a designer a second look at review time. Nothing gets built wrong.
:::

:::keyidea
There is no universal right threshold — only the question of which error a given
decision can least afford.
:::

## Confusion matrix and evaluation metrics

A confusion matrix sorts every case by what the model predicted and what actually
turned out to be true. Rows are predictions, columns are truth, and the diagonal is
where they agree.

- **Accuracy** = correct ÷ total
- **Precision** = TP ÷ predicted positive — *of what I called positive, how much really was?*
- **Recall** = TP ÷ actually positive — *of what really was positive, how much did I catch?*
- **F1** = harmonic mean of precision and recall

:::pylab{title="Precision and recall from a confusion matrix" packages=numpy}
# step: Work the numbers by hand once
TP, FP, FN, TN = 18, 5, 7, 47

accuracy  = (TP + TN) / (TP + FP + FN + TN)
precision = TP / (TP + FP)
recall    = TP / (TP + FN)
f1        = 2 * precision * recall / (precision + recall)

print(f"accuracy  {accuracy:.3f}")
print(f"precision {precision:.3f}   of what I called positive, how much really was")
print(f"recall    {recall:.3f}   of what really was positive, how much did I catch")
print(f"f1        {f1:.3f}")

# step: Watch accuracy lie when one class dominates
# 95 negatives, 5 positives, and a model that always says "negative"
print("\nA model that predicts the majority class every single time:")
print("accuracy  0.950   <- looks excellent")
print("recall    0.000   <- it never once found the thing you built it to find")
:::

## Class imbalance, uncertainty, and responsible use

{{Overfitting}} is not the only way to be misled. Accuracy alone misleads whenever one
class dominates: a model can score well overall by getting the common case right while
missing the rarer pattern it was actually built to find.

- Compare against a majority-class {{baseline}}, and report precision–recall rather
  than accuracy alone when the positive class is rare.
- Add an "uncertain — send to review" path when the model isn't confident, or the
  input falls outside its training range.
- Compare performance across relevant sites, building types, climates, and
  communities — not just in aggregate.
- Document who created the labels and how disagreements were resolved.

:::keyidea
A classifier learns patterns in its training data. It does not establish causation,
guarantee code compliance, or replace a licensed professional's judgment.
:::

## Cross-validation without building leakage

{{Cross-validation}} estimates {{generalization}} by rotating which slice of data is
held out. For architectural datasets the *grouping rule* matters as much as the number
of folds: all records from one building, site, simulation family, or adjacent time
period must stay in the same fold.

:::keyidea
If photographs of the same facade appear in both training and test sets, the test
score measures recognition of that facade rather than generalization to a new
building. That is {{data leakage}}, and it is silent.
:::
