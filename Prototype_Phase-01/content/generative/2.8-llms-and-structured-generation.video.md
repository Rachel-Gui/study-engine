:::scene{type=idea icon=bulb}
text: A language model does one thing. / It guesses the next word.
sub: Then it adds that word to the text, and guesses again. An essay, a design brief, a JSON file, a Python script — all of them come out of that one loop, one word at a time.
narration: |
  Here is the whole idea in one sentence. A language model does one thing: it guesses the
  next word. Then it adds that word to the text, and guesses again. And again. An essay, a
  design brief, a JSON file, a Python script: every one of them comes out of that single
  loop, one small piece at a time. Everything else in this lesson follows from this.
:::

:::scene{type=steps}
heading: The loop, step by step
steps:
  - Your prompt — the text so far
  - Guess the next word — the likeliest one, or a likely one
  - Add it — the text is now one word longer
  - Repeat — until the answer is done
narration: |
  Let's slow it down. First, your prompt: that is the text so far. Second, the model
  guesses the next word. Not the only possible word, but a likely one. Third, it adds that
  word to the text, so the text is now one word longer. Fourth, it repeats, hundreds of
  times, until the answer is done. That is it. There is no plan, no fact-checking, no
  understanding in the way you understand. Just a very, very good guesser.
:::

:::scene{type=code}
heading: A tiny language model, for real
code: |
  corpus = "the library has a timber roof and a glass facade . the pavilion has a timber roof ..."
  words = corpus.split()

  follows = {}                       # word -> what came after it, and how often
  for a, b in zip(words, words[1:]):
      follows.setdefault(a, {})
      follows[a][b] = follows[a].get(b, 0) + 1

  print(follows["timber"])
output: |
  {'roof': 3, 'frame': 1}
note: After the word "timber", the data saw "roof" three times and "frame" once. So the model's guess for the next word is "roof" — most of the time.
narration: |
  You can build a toy version of this in a few lines, and you will, in the lab on the
  website. Take six sentences about buildings. Count which word came after which. After
  the word timber, the data saw roof three times and frame once. So when the model is
  asked what comes after timber, it says roof, most of the time. Real models do exactly
  this, with a trillion words of data and a much cleverer way of counting. The counting
  is smarter. The idea is the same.
:::

:::scene{type=list}
heading: Why the answers sound so fluent
items:
  - Every word follows the last one naturally — that is what it was trained to do
  - So every sentence reads well — even when it is not true
  - The toy model wrote "the school faces the glass roof" — no sentence in its data said that
  - Two pieces that each fit together — made a claim nobody made
narration: |
  Now the important part. Because every word follows the previous one naturally, every
  sentence reads well. Even when it is not true. Our toy model wrote: the school faces the
  glass roof. No sentence in its data says that. Two pieces that each fit together made a
  claim nobody made. Real models do the same thing, less often and far more convincingly.
  That is what people mean by a hallucination. It is not a bug that will be fixed next
  year. It is the mechanism.
:::

:::scene{type=diagram id=llm_structured}
heading: Words in, structure out
points:
  - Text — for people to read
  - JSON — for code to read
  - Code — for a computer to run
  - A design representation — a room list, an adjacency graph
narration: |
  Here is why this matters for a designer. The same loop that writes prose can write
  anything that is written. Ask for a paragraph, you get text for people to read. Ask for
  JSON, and show one example of the shape, and you get JSON that a program can read. Ask
  for code, you get code a computer can run. Ask for a room list or an adjacency graph, and
  you get a design representation a model can use. This is called structured generation,
  and it is the bridge from a chat box to everything else in this course.
:::

:::scene{type=idea icon=warn}
text: Valid JSON is not a valid design.
sub: The model can return perfectly formatted JSON that says the window-to-wall ratio is 1.4. The format is right. The number is impossible.
narration: |
  But look at where the arrow ends in that figure. It does not go straight from the model
  to your tool. It goes through a check first. Because a model can return perfectly
  formatted JSON that says the window to wall ratio is one point four. The format is
  right. The number is impossible. A window to wall ratio can only be between zero and
  one. The model does not know that. You do. So you write it down as a rule.
:::

:::scene{type=code}
heading: The check, in plain Python
code: |
  RULES = {"floors": (int, (1, 60)),
           "wwr":    (float, (0.0, 1.0))}

  def validate(brief):
      problems = []
      for key, (kind, low_high) in RULES.items():
          if key not in brief:
              problems.append("missing: " + key)
          elif not low_high[0] <= brief[key] <= low_high[1]:
              problems.append(key + " is out of range")
      return problems
output: |
  validate({"floors": "three", "wwr": 1.4})
  ['wwr is out of range', ...]
note: Type, range, and "is it there at all" — three questions, asked by code, every single time.
narration: |
  Here is what that check looks like. A list of rules: floors must be a whole number
  between one and sixty. The window to wall ratio must be a number between zero and one.
  Then a small function that walks through the rules and collects the problems. Give it a
  reply that says three floors, written as a word, and a ratio of one point four, and it
  tells you exactly what is wrong. Type, range, and is it there at all. Three questions,
  asked by code, every single time. This is the difference between a chat and a tool.
:::

:::scene{type=cards}
heading: Where fluent answers go wrong
items:
  - title: An invented reference
    text: A paper title, authors and year that read perfectly and do not exist.
    tag: check the DOI
  - title: A confident number
    text: '"A 12 metre timber cantilever is typical." Where from? The model cannot say.'
    tag: find a source
  - title: Code that runs and is wrong
    text: A function that computes glazing area with the wrong denominator. No error appears.
    tag: test a case you know
narration: |
  Three ways fluent answers go wrong, and what to do about each. An invented reference: a
  paper title, authors and year that read perfectly and do not exist. Check it. A
  confident number: a twelve metre timber cantilever is typical. Where from? The model
  cannot tell you, so find a source. And code that runs and is wrong: a function that
  computes glazing area with the wrong number underneath, and no error appears anywhere.
  Test it on a case you can do by hand. In every case the fix is the same: the model
  proposes, and something outside the model checks.
:::
