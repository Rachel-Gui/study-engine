## What a language model does

A **large language model** (LLM) is the autoregressive approach from Lesson 2.1 applied
to text: it has learned, from a very large amount of writing, which token tends to
follow which context. To generate, it predicts the next token, appends it, and predicts
again. Everything an LLM produces — an essay, a design brief, a JSON file, a Python
script — comes out one token at a time from that single operation.

:::narration
A large language model does one thing: given everything so far, it predicts the next
token. Then it appends the prediction and predicts again. An essay, a design brief, a
JSON file and a Python script all come out of that one operation, one token at a time.
The lab below builds the smallest possible version of such a model, twenty lines that
count which word follows which. It is a toy, but it shows two things every real model
also does: it sounds fluent, because every step is locally plausible, and it can say
things its data never said, because plausible fragments can chain into a false
sentence. Keep that second behaviour in mind: it is the reason a fluent answer has to
be checked.
:::

:::cards
Token | a piece of text, roughly a short word or part of a word | the unit the model predicts
Context window | how much text the model can see at once | prompt, examples and the conversation so far
Temperature | how adventurous the sampling is | low: the likeliest token nearly every time; high: more variety, more nonsense
System prompt | standing instructions placed before your message | the "role" the model plays — this is what an agent is, in Module 4
:::

The lab builds a **bigram model**: for every word, count what followed it, then sample
from those counts. Real LLMs use a transformer that looks at thousands of tokens of
context rather than one word, and a vocabulary of tens of thousands of tokens — but the
generation loop is the same.

:::pylab{title="A language model in twenty lines"}
# step: Count what follows what
import random
corpus = """
the library has a timber roof and a glass facade .
the pavilion has a timber roof and a concrete base .
the museum has a concrete facade and a glass roof .
the school has a brick facade and a timber frame .
the library faces the park and the school faces the street .
the timber roof shades the glass facade in summer .
"""
words = corpus.split()
follows = {}                          # word -> {next word: count}
for a, b in zip(words, words[1:]):
    follows.setdefault(a, {})
    follows[a][b] = follows[a].get(b, 0) + 1

print("after 'the':", follows["the"])
print("after 'timber':", follows["timber"])
print("after 'glass':", follows["glass"])

# step: Generate by predicting the next word, again and again
def next_word(word, temperature=1.0):
    options = follows.get(word)
    if not options:
        return "."
    names = list(options)
    weights = [count ** (1 / temperature) for count in options.values()]
    return random.choices(names, weights)[0]

def generate(start, n=12, temperature=1.0):
    out = [start]
    for _ in range(n):
        out.append(next_word(out[-1], temperature))
        if out[-1] == ".":
            break
    return " ".join(out)

random.seed(1)
for _ in range(4):
    print(generate("the"))

# step: Temperature - how adventurous the sampling is
random.seed(1)
print("cold (0.2):")
for _ in range(3):
    print("  ", generate("the", temperature=0.2))
print("hot (3.0):")
for _ in range(3):
    print("  ", generate("the", temperature=3.0))

# step: Your turn - teach it something new
# The model can only say what its data says. Add one sentence to `corpus` that
# mentions "rammed earth", rebuild `follows`, and generate until "rammed" appears.
corpus = corpus + "\n"        # <- add your sentence here, ending with " ."
words = corpus.split()
follows = {}
for a, b in zip(words, words[1:]):
    follows.setdefault(a, {})
    follows[a][b] = follows[a].get(b, 0) + 1

random.seed(3)
lines = [generate("the", n=14) for _ in range(20)]
hit = [l for l in lines if "rammed" in l]
assert hit, "not yet - is your sentence in corpus, and did you rebuild follows?"
print(hit[0])
print("Correct!")
:::

Look at the sentences the model produced. Every word follows the previous one in a way
the corpus supports, so each sentence *reads* fine. But "the school faces the glass
roof" appears in no source sentence: two fragments that were each plausible chained
into a claim nobody made. That is a **hallucination**, in miniature. A model with a
billion times more data does it less often and more convincingly — it never stops
doing it.

:::predict
Same prompt, same model, and two different answers. What happened?
- The model changed its mind | A model has no mind to change between calls; it has no memory of the first call at all.
- *Generation samples; two runs draw different tokens | Yes. Unless the temperature is zero and everything else is fixed, two runs are two samples from the same distribution — exactly like two seeds in the diffusion lab.
- The second answer used more context | The context was identical. Sampling alone explains it.
:::

:::keyidea
**Fluency is a property of the process, not of the truth.** The model is rewarded for
producing the most plausible continuation. When the plausible continuation is also
true, that is because the training data or the context made it so — not because the
model checked.
:::

## Prompt and context in, structure out

The same next-token loop that writes prose can write anything that is written: a
table, a JSON object, a Grasshopper definition, a list of room adjacencies. This is the
capability that makes an LLM useful to *code*, and it is why this lesson sits between
the image-generation lessons and Modules 3 and 4.

:::figure{id=llm_structured caption="Figure 1. A prompt plus context goes in; text, JSON, code or a design representation comes out. The validator after the model is what makes the output safe for a tool or an agent to consume."}
:::

:::narration
The same loop that writes prose can write anything that is written. Ask for a table
and you get a table. Ask for JSON, and give an example of the shape, and you get JSON
that a program can read. This is structured generation, and it is the bridge between a
language model and everything else in the course: a script in Module three, an agent
in Module four. But notice where the arrow ends in the figure. It does not go straight
from the model to the tool. It goes through a validator, because a model can produce
JSON that parses perfectly and says the window-to-wall ratio is one point four.
:::

:::cards
Text | a brief, a rationale, a summary of a precedent | for people to read; checked by reading
JSON | {"wwr": 0.35, "orientation_deg": 180} | for code to read; checked by a schema and ranges
Code | a Python or Grasshopper script | for a machine to run; checked by running it on a known case
Design representation | an adjacency graph, a parameter set, a room schedule | for a model to consume; checked against the brief and the rules of the domain
:::

How do you get structure out reliably? Three things, in increasing strength:

1. **Ask for it, and show it.** "Respond only with JSON of this shape: {…}". An example
   of the format in the prompt does more than a description of it.
2. **Use the tool's structured mode.** Ollama's `format="json"` (Lesson 2.9) and the
   hosted APIs' JSON or schema modes constrain sampling so that only tokens that keep
   the output well-formed can be chosen. That guarantees the *shape* — never the
   *content*.
3. **Validate what came back.** Parse it, check every field's type and range, and
   refuse anything that fails. This is the only step that catches a plausible number
   that is wrong.

:::pylab{title="Read, then validate, a structured reply"}
# step: A reply that code can read
import json
reply = '''
{"project": "branch library", "site": "Seattle", "floors": 2,
 "wwr": 0.35, "orientation_deg": 180, "floor_to_floor_m": 4.2,
 "rooms": ["reading room", "children", "meeting", "staff"]}
'''
brief = json.loads(reply)          # text -> dictionary
print(type(brief).__name__, "with", len(brief), "fields")
print("WWR:", brief["wwr"], "  rooms:", len(brief["rooms"]))
print("glazing per floor at 40 x 20 m, 4.2 m floors:",
      round(2 * (40 + 20) * brief["floor_to_floor_m"] * brief["wwr"], 1), "m2")

# step: A validator - the rules the model cannot be trusted to follow
RULES = {
    "project":          (str,   None),
    "site":             (str,   None),
    "floors":           (int,   (1, 60)),
    "wwr":              (float, (0.0, 1.0)),
    "orientation_deg":  (float, (0.0, 360.0)),
    "floor_to_floor_m": (float, (2.4, 6.0)),
    "rooms":            (list,  None),
}

def validate(brief):
    problems = []
    for key, (kind, rng) in RULES.items():
        if key not in brief:
            problems.append(f"missing: {key}")
            continue
        value = brief[key]
        ok_type = isinstance(value, kind) or (kind is float and isinstance(value, int) and not isinstance(value, bool))
        if not ok_type:
            problems.append(f"{key}: expected {kind.__name__}, got {type(value).__name__} ({value!r})")
        elif rng and not (rng[0] <= value <= rng[1]):
            problems.append(f"{key}: {value} outside {rng}")
    return problems

print(validate(brief) or "valid")

# step: Fluent, well-formed, and wrong
reply2 = '''
{"project": "branch library", "floors": "three", "wwr": 1.4,
 "orientation_deg": 180, "floor_to_floor_m": 4.2,
 "rooms": "reading room, children, meeting, staff"}
'''
brief2 = json.loads(reply2)        # parses fine - the JSON is valid
for p in validate(brief2):
    print("-", p)

# step: Your turn - one more rule
# A brief also needs a total floor area between 200 and 20000 m2, as a number.
# Add "floor_area_m2" to RULES so that validate(brief3) reports exactly one problem.
brief3 = dict(brief, floor_area_m2=95)
# RULES["floor_area_m2"] = ...

problems = validate(brief3)
assert problems == ["floor_area_m2: 95 outside (200, 20000)"], problems or "no problem found - did you add the rule?"
print(problems[0])
print("Correct!")
:::

:::reflect{feedback="Valid JSON is a statement about syntax. The validator is where domain knowledge enters."}
A model returns JSON that parses without error. What has been established?
- The values in it are usable | Parsing only shows the shape is right. A WWR of 1.4 parses perfectly.
- *Only that the text is well-formed; every value still needs a check | Yes. Type, range and consistency with the brief are separate checks, and they are yours.
:::

:::details{summary="Show reference answer"}
`json.loads` succeeding means the reply is syntactically JSON. Whether the number of floors is an integer, whether the WWR is between 0 and 1, whether the rooms match the brief and whether the site is the one you asked about are all separate checks. A schema mode in the API can enforce types; ranges and consistency with your project are domain rules that only you can write.
:::

## Fluent is not verified

An LLM has no access to the world except through its training data and what you put in
its context. When you ask for a fact it has not seen — the floor area of your site, the
U-value of a specific assembly, a citation — it produces the most plausible-looking
answer. Nothing in the mechanism distinguishes a remembered fact from a well-formed
invention.

:::cards
An invented reference | a paper title, authors and year that read perfectly and do not exist | check every citation against the DOI or the journal
A confident number | "a 12 m timber cantilever is typical" | ask where the number comes from; the model cannot tell you, so find a source
Valid JSON with impossible values | WWR 1.4, three floors of 8 m in a 12 m building | the validator, then a person
Code that runs and is wrong | a function that computes glazing area with the wrong denominator | run it on a case you can check by hand (Module 3)
:::

:::narration
A language model has no access to the world beyond its training data and the context
you give it. Ask for a fact it has not seen, the area of your site, a U value, a
reference, and it produces the most plausible looking answer. Nothing in the mechanism
distinguishes a remembered fact from a well formed invention. So the evidence label for
anything a model writes is generated, not retrieved and not measured. Reducing the
problem is practical: put the facts into the context yourself, ask for structure so a
program can check it, validate it, and never ask a model for a number it could not
have seen. What remains is judgment, which is yours.
:::

The evidence labels this course uses everywhere apply here: what a model writes is
[[generated]], not [[retrieved]] and not [[measured]]. The label does not say the
output is wrong. It says the output has not been checked, and by whom it must be.

:::predict
A model describes the library image from Lesson 2.5: "three floors, a 12-metre cantilever, south-facing glazing." Which of these can you check, and how?
- None — the model saw the image, so it knows | Seeing is not measuring. The floor count was ambiguous to you in 2.5; it is ambiguous to the model too, and it will not say so.
- *All three, but only with information the image does not contain: plans and sections, a site plan, a structural drawing | Yes. Each claim is a hypothesis to verify with a document, not a fact to record.
- Only the cantilever, by asking again with a higher temperature | Temperature changes the variety of the answer, not its truth.
:::

:::details{summary="How to reduce hallucination, in practice"}
- **Put the facts in the context.** If the model needs your site area, give it your site area. Retrieval-augmented systems automate exactly this: search first, then generate from what was found.
- **Ask for structure, then validate.** A number in a JSON field can be range-checked; a number in a paragraph cannot.
- **Lower the temperature for extraction and conversion tasks.** Variety is a cost when the task is to restate what is in the context.
- **Ask for sources and check them.** A model can produce a citation; only a lookup can confirm it.
- **Do not ask for what the model cannot have.** The U-value of your specific wall build-up was not in its training data. Look it up, then give it to the model.
:::

## The bridge to code and agents

:::flow
Prompt + context > Language model > Structured output > Validator > A tool, a script, or an agent
:::

Everything after the model in this flow is what Modules 3 and 4 are about. In
**Module 3**, the structured output is code: the assistant writes a script, and your job
becomes reading and testing it. In **Module 4**, the model's structured output is a
message to another agent or a call to a tool, and the validator becomes a loop with
checks and a human gate. The next lesson, 2.9, installs a model on your own laptop so
that all of it runs without an API key.

:::keyidea
**A language model is a generator of plausible text, conditioned on your context.**
Used for what that is — drafting, restructuring, converting, proposing — it is
extraordinarily useful. Used as a source of facts or a substitute for a check, it fails
in the way this lesson demonstrated, and it fails fluently.
:::

:::boundary
Data | a corpus of six sentences in the lab; billions of documents in a real model
Evidence | everything a model writes is [[generated]]; the lab's outputs are reproducible with the seeds shown
Establishes | how next-token generation produces fluent text and, sometimes, false text; how structure plus validation makes output usable by code
Does not establish | that any particular model is accurate on any particular task; that a schema-valid answer is a correct one
:::
