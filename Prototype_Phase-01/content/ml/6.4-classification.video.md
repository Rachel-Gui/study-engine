:::scene{type=title}
narration: |
  Welcome to lesson six point four, classification: predicting a category. Is this
  facade brick or glass? Does this detail need a second look, or is it fine? A
  classifier answers questions like these, but not the way people expect: it gives you
  a score, and you have to decide what to do with it. This lesson is about that
  decision, about the four numbers that measure a classifier, and about the two ways
  the numbers can quietly lie.
:::

:::scene{type=list}
heading: Five things to define before you pick an algorithm
items:
  - The decision — what action will the prediction inform?
  - The prediction unit — one building, one facade image, one room, one sensor event?
  - The features — what is actually available at prediction time, not in hindsight
  - The target label — the labelling rule, written down, so two people would agree
  - The evaluation context — the building types, seasons and conditions the model will actually meet
narration: |
  Before any algorithm, five definitions. The decision: what action will this
  prediction inform? The prediction unit: are you classifying a building, a photo, a
  room, a single sensor event? The features: what is actually available at the moment
  of prediction, not what you know in hindsight. The target label: the labelling rule,
  written down, so that two people would label the same case the same way. And the
  evaluation context: the building types, seasons and conditions the model will
  actually meet. Skip any of these and the model will answer a question you did not
  mean to ask.
:::

:::scene{type=cards}
heading: Four shapes of classification
items:
  - title: Binary
    text: Two classes. Review now, or monitor.
    tag: yes / no
  - title: Multiclass
    text: One of several. Brick, glass, concrete or metal.
    tag: one of many
  - title: Multilabel
    text: Several labels at once. Door and window and desk.
    tag: many at once
  - title: Ordinal
    text: Classes with an order. Good, acceptable, poor.
    tag: ranked
narration: |
  Classification comes in four shapes. Binary: two classes, review now or monitor.
  Multiclass: one of several, brick, glass, concrete or metal. Multilabel: several
  labels on the same case, a photo that contains a door and a window and a desk. And
  ordinal: classes with an order, good, acceptable, poor. Most of this lesson is about
  binary, because that is where the threshold decision lives.
:::

:::scene{type=idea icon=bulb}
text: A classifier gives you a score. / You turn it into a decision.
sub: The score is between 0 and 1. It becomes a class only when you pick a threshold. 0.50 is a convention, not a law.
narration: |
  Here is the idea people miss. A binary classifier does not say yes or no. It gives
  you a score between zero and one. That score becomes a decision only when you pick a
  threshold: above this, call it a problem; below, call it fine. Zero point five is the
  default in most software. It is a convention, not a law. Lower the threshold and you
  catch more true cases, and raise more false alarms. Raise it and you get the reverse.
:::

:::scene{type=compare}
heading: Two ways to be wrong — and they do not cost the same
left:
  title: Called fine — actually a problem
  points:
    - Ships into a built, occupied building
    - Expensive, sometimes impossible, to fix afterwards
    - The error you usually cannot afford
right:
  title: Called a problem — actually fine
  points:
    - Costs a designer a second look at review time
    - Nothing gets built wrong
    - The error you can usually absorb
verdict: There is no universal right threshold — only the question of which error this decision can least afford.
narration: |
  Two ways to be wrong, and they do not cost the same. Suppose the model screens
  details for problems. Called fine but actually a problem: that ships into a built,
  occupied building, and it is expensive, sometimes impossible, to fix afterwards.
  Called a problem but actually fine: that costs a designer a second look at review
  time, and nothing gets built wrong. So for this decision you set the threshold to
  flag more, and you accept the extra second looks. There is no universal right
  threshold. There is only the question of which error this decision can least afford.
:::

:::scene{type=code}
heading: Four numbers from one confusion matrix
code: |
  TP, FP, FN, TN = 18, 5, 7, 47        # true/false positives and negatives

  accuracy  = (TP + TN) / (TP + FP + FN + TN)
  precision = TP / (TP + FP)   # of what I called positive, how much really was?
  recall    = TP / (TP + FN)   # of what really was positive, how much did I catch?
  f1        = 2 * precision * recall / (precision + recall)
output: |
  accuracy  0.844
  precision 0.783
  recall    0.720
  f1        0.750
note: A confusion matrix sorts every case by what the model said and what was true. Precision and recall each answer one plain question.
narration: |
  The confusion matrix sorts every case by what the model said and what turned out to
  be true. Four counts: true positives, false positives, false negatives, true
  negatives. From them, four numbers. Accuracy: the share it got right, eighty four
  percent here. Precision: of what I called positive, how much really was? Seventy
  eight percent. Recall: of what really was positive, how much did I catch? Seventy two
  percent. And F one, which folds precision and recall into one number when you need
  one. Learn the two plain questions, and you will never mix up precision and recall
  again.
:::

:::scene{type=number}
heading: Watch accuracy lie
items:
  - value: "95"
    label: of 100 photos show no defect
  - value: "0.950"
    label: accuracy of a model that always says "no defect"
    count: false
  - value: "0.000"
    label: its recall — it never once found the thing it was built to find
    count: false
narration: |
  Now watch accuracy lie. Ninety five of a hundred photos show no defect. A model that
  always says no defect scores ninety five percent accuracy, which looks excellent. Its
  recall is zero. It never once found the thing you built it to find. Whenever one
  class dominates, compare against this do nothing baseline, and report precision and
  recall, not accuracy alone.
:::

:::scene{type=idea icon=warn}
text: Same facade in training and test? / You measured recognition, not generalization.
sub: All records from one building, site, simulation family or adjacent time period stay in the same fold. That is data leakage, and it is silent.
narration: |
  One more silent failure. Cross validation estimates how the model does on new data
  by rotating which slice is held out. For buildings, the grouping rule matters as much
  as the number of folds. If photographs of the same facade appear in both training and
  test, the test score measures recognition of that facade, not generalization to a new
  building. Keep all records from one building, one site, one simulation family, or one
  stretch of time in the same fold. This is data leakage, and nothing will warn you.
:::

:::scene{type=list}
heading: Using a classifier responsibly
items:
  - Compare against the majority-class baseline before you celebrate
  - Report precision and recall when the positive class is rare
  - Add an "uncertain — send to review" path for low-confidence cases
  - Say what the model does not do — cause, code compliance, a licensed professional's judgment
narration: |
  Using a classifier responsibly. Compare against the majority class baseline before
  you celebrate. Report precision and recall, not accuracy, when the thing you are
  looking for is rare. Add a path for uncertain cases: send them to a human rather than
  forcing a yes or no. And say what the model does not do. It learns patterns in its
  training data. It does not establish cause, it does not guarantee code compliance,
  and it does not replace a licensed professional's judgment.
:::
