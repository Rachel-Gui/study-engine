## The design is the rule, not the drawing

A drawing shows one building. A program describes a **family** of buildings: every
width, depth, floor count and glazing ratio the rule allows, and a number for each of
them. When the design lives in code, changing your mind costs one keystroke, a hundred
variants cost one loop, and the reasons for a choice are written down where a
reviewer can run them.

That is what "code as a design medium" means. Not that architects should become
programmers, but that a rule you can execute is a different kind of design object
from a picture you can only look at — and that with an assistant writing the code,
the rule is now within reach of anyone who can describe it precisely.

:::compare
A drawing | one instance | you see it; you cannot ask it anything
A program | a family of instances, with a metric for each | you sweep it, sort it, plot it; the drawing is one output among many
:::

:::cards
Parameter | a number you choose: width, depth, floors, WWR | the inputs of the family
Rule | how the parameters become a building and its numbers | the function
Variant | one setting of the parameters | one call of the function
Metric | a number that says something about a variant | area, compactness, a daylight proxy — and later, a simulated load
:::

Grasshopper, Dynamo and every parametric tool are this idea with wires instead of
lines of text. Python is the same idea with less to click and more to read. Everything
in this lesson runs in the browser; on your own machine it would run inside Rhino or
Revit just as well.

## A first design tool, in thirty lines

The lab builds the smallest useful design tool: a rectangular bar building described
by four parameters, returning five numbers — floor area, glazing area, envelope,
surface-to-volume ratio (a compactness measure; lower means less envelope per unit of
volume) and a **daylit fraction**: the share of the floor plate within six metres of a
facade. Six metres is a rule of thumb, not a simulation, and the boundary card at the
end says so.

:::pylab{title="A bar building as a rule" packages=matplotlib}
# step: A building as a rule
def bar(width, depth, floors, wwr, f2f=3.6, reach=6.0):
    """A rectangular bar building. Lengths in metres. Returns the numbers a
    massing study needs: areas, envelope, compactness and a daylight proxy."""
    plate = width * depth
    floor_area = plate * floors
    height = floors * f2f
    walls = 2 * (width + depth) * height
    envelope = walls + plate                       # walls + roof
    volume = plate * height
    inner = max(0, width - 2 * reach) * max(0, depth - 2 * reach)   # plate further than `reach` from any facade
    return {
        "floor_area_m2": floor_area,
        "glazing_m2": round(walls * wwr, 1),
        "envelope_m2": round(envelope, 1),
        "s_over_v": round(envelope / volume, 3),   # surface-to-volume: lower is more compact
        "daylit_fraction": round(1 - inner / plate, 3),
    }

for key, value in bar(40, 16, 3, 0.35).items():
    print(f"{key:>18}: {value}")

# step: Sweep one parameter, keep the rest fixed
import matplotlib.pyplot as plt
depths = list(range(10, 41, 2))
runs = [bar(40, d, 3, 0.35) for d in depths]

fig, ax1 = plt.subplots(figsize=(7, 3.6))
ax1.plot(depths, [r["daylit_fraction"] for r in runs], "-o", color="#4b2e83", label="daylit fraction")
ax1.set_xlabel("depth (m), width fixed at 40 m, 3 floors")
ax1.set_ylabel("daylit fraction", color="#4b2e83")
ax2 = ax1.twinx()
ax2.plot(depths, [r["s_over_v"] for r in runs], "-s", color="#b7a57a", label="surface / volume")
ax2.set_ylabel("surface / volume (1/m)", color="#b7a57a")
ax1.grid(alpha=.3)
_ = fig.suptitle("Deeper plates are more compact and less daylit: the trade-off, as a curve")

# step: Draw the variant the numbers describe
def draw(width, depth, reach=6.0):
    fig, ax = plt.subplots(figsize=(6, 3.2))
    ax.add_patch(plt.Rectangle((0, 0), width, depth, fill=False, lw=2, color="#111"))
    iw, id_ = width - 2 * reach, depth - 2 * reach
    if iw > 0 and id_ > 0:
        ax.add_patch(plt.Rectangle((reach, reach), iw, id_, color="#4b2e83", alpha=.25))
        ax.text(width / 2, depth / 2, "beyond daylight reach", ha="center", va="center", fontsize=9)
    ax.set_xlim(-2, width + 2); ax.set_ylim(-2, depth + 2)
    ax.set_aspect("equal"); ax.axis("off")
    _ = ax.set_title(f"{width} x {depth} m plate, daylit fraction {bar(width, depth, 3, 0.35)['daylit_fraction']}")

draw(40, 16)
draw(40, 28)

# step: Your turn - search the family
# Find the largest whole-metre depth (width 40 m, 3 floors) whose daylit fraction is
# at least 0.8. Put it in `best_depth`. A loop over range(10, 41) and one `if` will do.
best_depth = None

assert best_depth == 16, f"not yet - got {best_depth}"
print("largest depth with >= 80% daylit:", best_depth, "m")
print("Correct!")
:::

:::narration
Step one is the rule: four parameters in, five numbers out. Step two is where code
stops being a calculator and becomes a design medium. One loop produces sixteen
variants, and the plot shows the trade off the whole family contains: deeper plates
are more compact and less daylit, and the two curves put a number on what each metre
of depth buys and costs. Step three draws the variant behind any point on them. Step four asks the tool a
question no drawing can answer: what is the deepest plate that still keeps eighty
percent of the floor within reach of a window?
:::

:::predict
The sweep shows a deep plate is more compact and a shallow plate is more daylit. The tool has computed both curves correctly. What has it *decided*?
- The best depth — the point where the two curves come closest | There is no such point in the tool. Which depth is best depends on how much you value daylight against envelope, and nothing in the code weighs one against the other. Change the reach from 6 m to 8 m and both curves move. Deciding is yours.
- *Nothing. It has made a trade-off visible so that a person can decide | Yes. A tool that ranks variants by a metric you wrote has your judgment baked into the metric, not the tool's.
- That daylight matters more than compactness | The plot gives the two metrics equal visual weight because you gave them equal axes. Nothing in the code weighs them.
:::

## From a prompt to a tool

The lab's function is exactly the kind of thing an assistant writes well — *if the
brief is precise*. Compare the brief that produced the bugs in Lesson 3.1 ("write a
function for the window-to-wall ratio") with a brief that leaves nothing to guess:

:::cards
Purpose | one sentence: what the tool is for and who reads its output | "a massing study tool for early design; the numbers go into a comparison table"
Inputs, with units | every parameter, its unit, and a sensible range | "width and depth in metres (8–80), floors (1–20), WWR (0–1)"
Outputs, with units | every number it returns and what it means | "floor area m², glazing m², envelope m², surface/volume 1/m, daylit fraction 0–1"
One worked example | a case with the numbers you expect | "40 × 16 m, 3 floors, WWR 0.35 → floor area 1920 m², daylit fraction 0.825"
Constraints | what it must not do | "no external libraries except matplotlib; pure functions; no input prompts"
:::

:::keyidea
**The worked example is the test.** When the brief contains a case with its expected
answer, the assistant has a target, and you have an assertion to paste under the code.
Every brief in the Lesson 3.4 workshop carries one. If you cannot write the worked
example, you are not ready to ask for the tool — and finding that out is useful.
:::

:::narration
The lab's function is exactly what an assistant writes well, if the brief is precise.
A brief that leaves nothing to guess has five parts: the purpose in one sentence,
every input with its unit and range, every output with its unit, one worked example
with the numbers you expect, and the constraints. The worked example is the test.
Paste it under the code as an assertion and the loop closes. If you cannot write the
worked example, you are not ready to ask for the tool, and finding that out is
useful.
:::

:::reflect{feedback="A precise brief is the design work; the code is its transcription."}
Which part of a design-tool brief does the most to prevent the two bugs from Lesson 3.1?
- The purpose sentence | Useful for the assistant's choices, but "window-to-wall ratio" was already in the purpose and it was still misread.
- *Inputs and outputs with units, and a worked example with its expected number | Yes. "sun altitude in degrees" removes the unit bug; "one 3 × 2 window in a 10 × 3 wall gives 0.2" removes the definition bug.
- The constraints | They prevent a different class of problem — the wrong library, an input prompt that hangs a script.
:::

:::details{summary="Show reference answer"}
The definition bug (glazing over opaque wall) could not survive a worked example whose expected value was 0.2; the unit bug could not survive "altitude in degrees" in the inputs list. Purpose and constraints matter for other reasons, but the two parts that carry numbers are the ones that make the code checkable.
:::

## What the tool cannot judge

A daylit fraction from a six-metre rule is a proxy. It tells you, quickly, that a
28-metre-deep plate has a dark middle. It does not tell you the daylight autonomy of
any room, which depends on orientation, glazing, obstructions, the sky and the
schedule. Modules 5 to 8 are about replacing proxies with measured or simulated
evidence and knowing which is which. The design tool's role is earlier and humbler:
to make a whole family visible so that the expensive evaluation is spent on the right
few members.

:::keyidea
**Code makes the design space visible. It does not judge it.** Every metric in the
tool is a rule you wrote; the tool is only as good as the rules, and the rules are
only as good as the evidence behind them.
:::

:::boundary
Data | a rectangular bar building rule with a six-metre daylight-reach rule of thumb; no site, climate or schedule
Evidence | every number the tool prints is [[model-predicted]] by a rule you can read; none is measured or simulated
Establishes | how a parametric rule turns four parameters into comparable numbers; how a sweep exposes a trade-off; the shape of a brief an assistant can act on
Does not establish | daylight autonomy, energy use or any code compliance of any variant; that the six-metre rule holds for a given glazing, orientation or sky
:::
