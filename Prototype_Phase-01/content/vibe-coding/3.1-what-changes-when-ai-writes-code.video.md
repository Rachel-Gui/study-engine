:::scene{type=idea icon=bulb}
text: Vibe coding — / describe it, accept the code, paste the errors back.
sub: Andrej Karpathy named it in February 2025. This module uses it with one change — after describe, generate and run, we read.
narration: |
  In February twenty twenty five, Andrej Karpathy gave a name to something many people
  were already doing: describing what you want in plain language, accepting the code a
  model writes, pasting the error messages back when it fails, and never quite reading
  the code. He called it vibe coding. This module uses the term with one change. We
  describe, we generate, we run, and then we read. For a throwaway script the vibe is
  enough. For a tool whose numbers end up in a design decision, the reading is the job.
:::

:::scene{type=diagram id=vibe_loop}
heading: The loop
narration: |
  Here is the loop. Describe: what you want, for whom, the inputs, the outputs, one
  example. Generate: the assistant writes the code. Run: execute it on a real case.
  Read: does it do what you said, line by line? Refine: narrow the brief, add a test, ask
  again. The loop runs three to ten times for a small tool. The machine does the
  generating and the running. The gold steps, describing precisely and reading
  critically, are yours, and they decide whether the tool can be trusted.
:::

narration: |
  Three kinds of assistant, and they all produce the same thing: generated code. A chat
  assistant in a browser tab, where you paste code and errors back and forth, and
  nothing runs on its own. An editor assistant inside VS Code, which completes as you
  type and sees your open files. And an agentic tool in a terminal, which reads your
  whole project, edits files, runs commands and asks before doing anything risky. The
  agentic tools are the most powerful, and the easiest to stop reading.
:::

narration: |
  What is it good at? Exactly the parts of programming that used to take the most
  typing: boilerplate, library syntax, a first draft, an explanation of an error. What
  is it bad at? The parts that need the world rather than the training data. It does
  not know what you meant. It does not notice that your heights are in centimetres. It
  does not know what your data looks like. And it almost never says that it is unsure.
:::

:::scene{type=code}
heading: A function the assistant wrote — it runs
code: |
  def wwr(windows, walls):
      """Window-to-wall ratio of a facade."""
      glazing = sum(w * h for w, h in windows)
      wall = sum(l * h for l, h in walls)
      return glazing / (wall - glazing)

  print(wwr([(3, 2)], [(10, 3)]))
output: |
  0.25
note: Brief given to the assistant — "Return the window-to-wall ratio." One wall of 10 by 3 m and one window of 3 by 2 m. Is 0.25 right?
narration: |
  Here is a function an assistant wrote from a one sentence brief: return the window to
  wall ratio. It has a docstring, it runs, and it prints zero point two five. One wall,
  ten metres by three. One window, three by two. Is zero point two five right? Do it in
  your head. Six square metres of glass over thirty square metres of wall is zero point
  two. The function divided by the wall minus the glass: glazing over opaque wall. A
  real quantity, just not the one the brief named. It ran without a single error.
:::

:::scene{type=cards}
heading: The risks that come with the speed
items:
  - title: You cannot review what you cannot read
    text: That is why Module 1 exists.
  - title: '"It works on the example"'
    text: One passing case proves one case. Test a second path and the edges.
  - title: Silent unit errors
    text: Degrees and radians, metres and millimetres. Put the unit in every name.
  - title: What you paste leaves your machine
    text: No keys, no private data, no client files in a hosted chat. A local model sees nothing but your laptop.
narration: |
  The speed has costs, and they are predictable. You cannot review what you cannot
  read, which is why this course taught Python before it let a model write it. One
  passing example proves one example: test a second path and the edges. Units fail
  silently, degrees and radians, metres and millimetres, so put the unit in every name.
  And anything you paste into a hosted assistant leaves your machine: no keys, no
  private data, no client files, or use a local model, which sees nothing but your
  laptop.
:::

:::scene{type=idea icon=warn}
text: Generated code is a hypothesis / about what you meant.
sub: Running a test turns it into evidence. Confidence is a style. The test is the signal.
narration: |
  The sentence to keep. Generated code is a hypothesis about what you meant. Running a
  test turns it into evidence: measured behaviour on a case you understand. The wrong
  answer arrives in exactly the tone of the right one, so confidence is a style, not a
  signal. The test is the signal.
:::

:::scene{type=diagram id=code_comprehension_loop}
heading: What the evidence says about reading assistant-written code
points:
  - "The work moves — from writing code to comprehending, refining and integrating it"
  - "93 % of generated explanations had something correct — and 50 % something incorrect"
  - "Code plus the error message — one tool's perfect-fix rate rose from 11 % to 78 %"
  - "Over-dependence \"might diminish the ability to comprehend code independently\""
narration: |
  This is not only the course's opinion. A twenty twenty six systematic review by Qiao,
  Shihab and Hundhausen read thirty one studies of A I assistants used to understand
  code, and its framing is the one this module takes: the work shifts from writing
  code to comprehending, refining and integrating code the model wrote. Three findings
  sharpen every step of the loop. Assistants explain code well but not reliably: in
  one study, ninety three percent of generated explanations contained something
  correct and fifty percent contained something incorrect, at the same time. So an
  explanation is not a check; that is a measured fact. Context is the biggest lever:
  giving the assistant the code and the error together raised one tool's perfect fix
  rate from eleven percent to seventy eight. That is why every debugging prompt in
  this course pastes both. And speed is not learning: some studies found assistants
  cut task time without improving understanding, and the review warns that over
  dependence might diminish the ability to comprehend code independently. Its advice
  for teaching is the loop you just saw: evaluate, debug and explain generated code
  before you use it.
:::

  To remember. The loop is describe, generate, run, read, refine, and the reading is
  yours. Assistants are good at the typing heavy parts and bad at knowing what you

  every name, a second test case, and nothing private into a hosted chat. Generated
  code is a hypothesis; a test makes it evidence. And the research agrees: explanations
  are often half right, context doubles the fix rate, and speed is not learning.
:::
