## The brief

Build one small design tool with an assistant — any assistant: Claude Code on your
local model (3.3), or a chat model in a browser tab. The tool is the deliverable; the
**record** of how it was made is what gets reviewed. Work in pairs if you can: one
person drives the assistant, the other reads every line before it is accepted, then
swap.

:::narration

Pick one, or write your own with the same five parts:

:::cards
A · Solar overhang | inputs: window height (m), sun altitude (°) → output: overhang depth (m) | worked example: 1.5 m window, sun at 45° → 1.5 m; then extend it with latitude and date if you finish early
B · Room schedule checker | inputs: a list of rooms with areas (m²) and a brief with required areas → output: which rooms are under, over, or missing | worked example: brief asks for a 60 m² reading room; schedule has 48 m² → "reading room: 12 m² under"
C · Massing comparison | inputs: several bar buildings as (width, depth, floors, WWR) → output: a table sorted by a metric you choose, plus a plot | worked example: the 40 × 16 × 3 bar from Lesson 3.2 has daylit fraction 0.825
:::

:::flow
Write the brief > Ask > Run the worked example > Read every line > Refine, once per issue > Record > Review
:::

## Run the loop, deliberately

1. **Write the brief before opening the assistant.** Purpose, inputs with units,
   outputs with units, one worked example with its expected number, constraints.
   The template is in Lesson 3.2. If you cannot fill in the worked example, choose a
   smaller tool.
2. **Ask once, completely.** Paste the whole brief. Do not drip-feed it; a model
   that sees the constraints late rewrites everything.
3. **Run the worked example first.** Before reading, before admiring. If the number
   is wrong, that is your first refinement, and you already know where to look.
4. **Read every line**, with the checklist below. Reading means you can say, for each
   line, what it does and why it is there. A line you cannot explain is a line you
   remove or ask about.
5. **Refine one issue per message.** "The altitude is in degrees; convert to radians
   before `tan`." Not "fix it". Each message goes in the record.
6. **Stop when the tests pass and you can explain the code** — not when the assistant
   says it is done.

:::keyidea
**The assistant's "done" is not a state of the code.** It is a state of the
conversation. Your tests passing, and your ability to explain every line, are states
of the code.
:::

## The review checklist

Use it on the other person's tool, then on your own. Every "no" is a refinement
message.

:::cards
Does the worked example pass? | the brief's case, as an assertion | if not, nothing else matters yet
Does a second case pass? | a different path: two windows, a low sun, a missing room | one case proves one case
Are units in the names? | `window_height_m`, `sun_altitude_deg` | the unit bug from 3.1 cannot hide in a name that says degrees
Can you explain every line? | including the ones that look like boilerplate | an unexplained line is a guess the model made for you
Does it fail loudly? | a negative height, an altitude of 95°, an empty list | a tool that returns a number for nonsense input will be trusted with nonsense
Is anything hard-coded that should be an input? | 6 m reach, 3.6 m floors, Seattle | a hidden constant is a design decision nobody made
Would it run on a clean machine? | only the libraries the brief allowed | an import that only works on the assistant's imagined setup is a future error
What does the record say it does not establish? | the boundary card, in your words | a tool with no stated limits has unstated ones
:::

## Keep the record

The record makes the tool reproducible and reviewable: the brief, the assistant and
model used, each iteration's prompt and what it changed, and the test results at the
end. It is the same discipline as the generation record in Lesson 2.6, applied to
code. The lab below builds one; adapt it to your tool.

:::pylab{title="A reproducible record for an assistant-built tool"}
# step: The record, before any code exists
import json
record = {
    "tool": "solar_overhang",
    "purpose": "size a south-facing overhang for early design; numbers go into a comparison table",
    "inputs": {"window_height_m": "0.5-4", "sun_altitude_deg": "10-80"},
    "outputs": {"overhang_depth_m": "horizontal projection that fully shades the window"},
    "worked_example": {"window_height_m": 1.5, "sun_altitude_deg": 45, "overhang_depth_m": 1.5},
    "constraints": ["pure function", "no external libraries", "degrees in, metres out"],
    "assistant": "local qwen3 via Claude Code",
    "iterations": [],
}
print(json.dumps(record, indent=2)[:400], "...")

# step: The tests, written from the worked example
import math
def overhang_depth(window_height_m, sun_altitude_deg):
    return window_height_m / math.tan(math.radians(sun_altitude_deg))

tests = [
    ((1.5, 45), 1.5),           # the worked example from the brief
    ((2.0, 60), 1.1547),        # a second angle
    ((1.0, 30), 1.7321),        # a low sun needs a deep overhang
]
def run_tests(fn, tests):
    results = []
    for args, expected in tests:
        got = fn(*args)
        results.append({"args": args, "expected": expected, "got": round(got, 4),
                        "pass": abs(got - expected) < 1e-3})
    return results

for r in run_tests(overhang_depth, tests):
    print("PASS" if r["pass"] else "FAIL", r["args"], "->", r["got"], "expected", r["expected"])

# step: Log the iteration
record["iterations"].append({
    "n": 1,
    "prompt": "Write overhang_depth(window_height_m, sun_altitude_deg) ... (the brief above)",
    "what_changed": "first version used degrees directly; asked for radians conversion",
    "tests": run_tests(overhang_depth, tests),
})
record["all_pass"] = all(t["pass"] for t in record["iterations"][-1]["tests"])
print(json.dumps(record["iterations"][-1], indent=2))
print("all tests pass:", record["all_pass"])

# step: Your turn - add an edge case
# Add a test to `tests` for a 1.2 m window with the sun at 80 degrees (expected 0.2116),
# rerun run_tests, and store its last result in `edge`.
edge = None

assert edge is not None and edge["pass"] and edge["args"] == (1.2, 80), "not yet - add the case, rerun run_tests, keep its last entry"
print("edge case:", edge)
print("Correct!")
:::

:::narration
The record is the same discipline as the generation record in lesson two point six,
applied to code. It starts before any code exists, with the brief. Then come the
tests, written from the worked example, and one more case that takes a different
path. Each iteration logs the prompt, what changed, and the test results. When the
record says all tests pass, that is a statement about the code, made by code, and
anyone can rerun it.
:::

## Deliverable and rubric

Submit two files: the tool (`.py`), and the record (`.json` or `.md`). The record
should let someone who was not in the room reproduce the tool with the same
assistant, and see every refinement you asked for.

:::cards
The brief | complete: purpose, inputs and outputs with units, worked example, constraints | 25%
The tests | the worked example plus at least two more cases, all passing, one of them an edge or failure case | 25%
The reading | you can explain every line; nothing hard-coded that should be an input; units in the names | 25%
The record | every iteration's prompt and change; the assistant and model; a boundary statement in your words | 25%
:::

## Reflect on the loop

:::reflect
Where did the assistant save you the most time, and where did it cost you time?
:::

:::details{summary="Show reference answer"}
Most pairs report that the first draft arrived in seconds and the boilerplate was flawless — and that the time went into the brief (which they had never written so precisely before), into the one line that was subtly wrong, and into deciding what to test. That distribution is the point: the typing moved to the machine; the thinking did not.
:::

:::reflect
Which line in your tool did you find hardest to explain, and what did you do about it?
:::

:::details{summary="Show reference answer"}
A good answer names the line and says one of three things: I asked the assistant to explain it and checked the explanation against the documentation; I replaced it with something I understood; or I removed it and the tests still passed, so it was not needed. "I left it because it worked" is the answer the checklist exists to prevent.
:::

:::reflect
What does your tool establish, and what does it not?
:::

:::details{summary="Show reference answer"}
For the overhang tool: it establishes the geometric depth for a given altitude — a [[model-predicted]] number from a rule you can read. It does not establish the altitude for your site and date (that needs a solar position calculation or a table), the effect of a fin or of diffuse light, or whether the overhang is a good idea for heating season. Modules 5 to 8 are where the evidence for those questions comes from.
:::

:::keyidea
**A vibe-coded tool is finished when it is tested, read and recorded — by you.** The
assistant made it fast. The checklist made it trustworthy. Module 4 takes the same
loop one step further and lets the model call tools on its own; the gate you were in
this workshop is the gate you will design there.
:::

:::boundary
Data | one small design tool per pair; hand-calculable test cases
Evidence | the tool's code is [[generated]]; each test result is [[measured]]; the boundary statement is [[human]] judgment
Establishes | that a bounded design tool can be built and verified with an assistant in an hour; the record that makes it reproducible
Does not establish | the tool's validity beyond its tested cases; anything about the site, climate or performance the tool's rule does not contain
