  Welcome to lesson three point four, the hands-on lesson: vibe code a design tool. In about an
  hour, in pairs, you will take a small design tool from a written brief to tested code
  with an assistant, and keep a record that lets someone else reproduce every step. The
  tool is the deliverable. The record is what gets reviewed.
:::

narration: |
  Pick one of three briefs, or write your own with the same five parts. A: a solar
  overhang tool. Window height and sun altitude in, overhang depth out. B: a room
  schedule checker. A list of rooms with areas and a brief with required areas in;
  which rooms are under, over or missing, out. C: a massing comparison. Several bar
  buildings in; a table sorted by a metric you choose, plus a plot, out. Every brief
  comes with a worked example, and the worked example is your first test.
:::

:::scene{type=steps}
heading: Run the loop, deliberately
steps:
  - Write the brief — before opening the assistant
  - Ask once, completely — paste the whole brief
  - Run the worked example — before reading, before admiring
  - Read every line — with the checklist
  - Refine — one issue per message
  - "*Stop — when the tests pass and you can explain every line"
narration: |
  Run the loop deliberately. Write the brief before you open the assistant: purpose,
  inputs with units, outputs with units, one worked example, constraints. Ask once,
  completely; do not drip feed it. Run the worked example first, before reading,
  before admiring. Then read every line with the checklist. Refine one issue per
  message: the altitude is in degrees, convert to radians before tan. Not fix it. And
  stop when the tests pass and you can explain every line. Not when the assistant says
  it is done.
:::

:::scene{type=idea icon=warn}
text: The assistant's "done" / is not a state of the code.
sub: It is a state of the conversation. Your tests passing, and your ability to explain every line, are states of the code.
narration: |
  This is the sentence to carry into the hour. The assistant's done is not a state of
  the code. It is a state of the conversation. Your tests passing, and your ability to
  explain every line, are states of the code. A line you cannot explain is a line you
  remove or ask about.
:::

:::scene{type=list}
heading: The review checklist
items:
  - Does the worked example pass? — if not, nothing else matters yet
  - Does a second case pass? — a different path, an edge, a failure
  - Are units in the names? — window_height_m, sun_altitude_deg
  - Can you explain every line? — including the ones that look like boilerplate
  - Does it fail loudly? — a negative height, an altitude of 95°, an empty list
  - Is anything hard-coded that should be an input? — a hidden constant is a decision nobody made
narration: |
  The checklist. Use it on your partner's tool, then on your own, and every no is a
  refinement message. Does the worked example pass? If not, nothing else matters yet.
  Does a second case pass, a different path, an edge, a failure? Are the units in the
  names? Can you explain every line, including the ones that look like boilerplate?
  Does it fail loudly on nonsense input, a negative height, an altitude of ninety five
  degrees? And is anything hard coded that should be an input? A hidden constant is a
  design decision nobody made.
:::

:::scene{type=code}
heading: The record — the same discipline as Lesson 2.6, applied to code
code: |
  tests = [((1.5, 45), 1.5),        # the worked example from the brief
           ((2.0, 60), 1.1547),     # a second angle
           ((1.0, 30), 1.7321)]     # a low sun needs a deep overhang

  def run_tests(fn, tests):
      return [{"args": a, "expected": e, "got": round(fn(*a), 4),
               "pass": abs(fn(*a) - e) < 1e-3} for a, e in tests]

  record["iterations"].append({"n": 1, "prompt": "...",
      "what_changed": "asked for radians conversion",
      "tests": run_tests(overhang_depth, tests)})
output: |
  PASS (1.5, 45) -> 1.5     expected 1.5
  PASS (2.0, 60) -> 1.1547  expected 1.1547
  PASS (1.0, 30) -> 1.7321  expected 1.7321
note: The record starts before any code exists — with the brief — and ends with test results made by code, which anyone can rerun.
narration: |
  The record is the same discipline as the generation record in lesson two point six,
  applied to code. It starts before any code exists, with the brief. Then come the
  tests, written from the worked example, plus a second case that takes a different
  path. Each iteration logs the prompt you sent, what changed, and the test results.
  When the record says all tests pass, that is a statement about the code, made by
  code, and anyone can rerun it.
:::

:::scene{type=quiz}
question: Your tool passes the worked example. Which of these is the best next test?
options:
  - The same case again, to be sure
  - A case that takes a different path — a low sun, two windows, or nonsense input
  - Ask the assistant to write more tests and accept them
answer: 1
pause: 5
explain: One passing case proves one case. A second path catches what the first happened to miss; a nonsense input shows whether the tool fails loudly. Tests the assistant writes need the same reading as its code.

  windows, or nonsense input. C: ask the assistant to write more tests and accept

:::

:::scene{type=cards}
heading: The rubric
items:
  - title: The brief · 25%
    text: Purpose, inputs and outputs with units, worked example, constraints.
  - title: The tests · 25%
    text: The worked example plus two more cases, all passing, one an edge or failure case.
  - title: The reading · 25%
    text: You can explain every line. Units in names. Nothing hard-coded that should be an input.
  - title: The record · 25%
    text: Every iteration's prompt and change, the assistant and model, and a boundary statement in your words.
narration: |
  How it is graded. The brief, twenty five percent: purpose, inputs and outputs with
  units, a worked example, constraints. The tests, twenty five: the worked example plus
  two more cases, all passing, one of them an edge or failure case. The reading, twenty
  five: you can explain every line, units are in the names, nothing is hard coded that
  should be an input. And the record, twenty five: every iteration's prompt and change,
  the assistant and model used, and a boundary statement in your own words, what the
  tool does and does not establish.
:::
