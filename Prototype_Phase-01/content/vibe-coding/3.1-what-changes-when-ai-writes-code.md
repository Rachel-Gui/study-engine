## Vibe coding, defined

In February 2025 Andrej Karpathy gave a name to something many people were already
doing: describing what you want in plain language, accepting the code a model writes,
pasting the error messages back when it fails, and never quite reading the code.
He called it **vibe coding**, and within months the phrase was everywhere.

This module uses the term with one deliberate change. We describe, we generate, we
run — and then **we read**. For a throwaway script, the vibe is enough. For a tool
whose numbers end up in a design decision, the reading is the job.

A year later, in February 2026, Karpathy himself retired the term for serious work
and proposed **agentic engineering** instead: "agentic" because the new default is
that you are not writing the code directly, you are orchestrating agents who do and
acting as oversight; "engineering" to insist that there is an art, a science and an
expertise to it. Vibe coding, in his own account, was for fun throwaway projects,
demos and explorations. The oversight is exactly this module's one change; the
orchestration is Module 4.

:::cards
Chat assistant | ChatGPT, Claude, Gemini in a browser tab | you paste code and errors back and forth; free tiers exist; nothing runs on its own
Editor assistant | Copilot, Cursor, Windsurf inside VS Code | completes lines as you type and edits selected code; sees your open files
Agentic tool | Claude Code, Codex CLI, Gemini CLI in a terminal | reads your whole project, plans, edits files, runs commands, asks before risky steps — an agent, in Module 4's sense
:::

All three produce the same thing: [[generated]] code. What differs is how much of the
loop they run for you. The agentic tools are the most powerful and the easiest to stop
reading — Lesson 3.3 sets one up on your own laptop so you can watch it work.

:::predict
You ask an assistant for "a script that computes the window-to-wall ratio of my facade". It returns a clean function with a docstring and it runs without error. What do you know?
- The function is correct — it ran, and the docstring says what it does | Running without error means the syntax is fine. The docstring was written by the same model that wrote the code; it is not a check.
- *Only that it runs. Whether it computes the ratio you meant is not yet established | Yes. A test on a case you can do by hand is what establishes that, and it takes one minute.
- It is wrong, because models cannot do arithmetic | Models write arithmetic code perfectly well most of the time. The failure is subtler: a plausible interpretation of the brief that is not yours.
:::

## What the assistant is good at, and what it is bad at

:::compare
Good at | boilerplate, library syntax, a first draft, explaining an error message, converting between formats, naming things | the tedious, well-documented parts — where most of the typing used to go
Bad at | knowing what you meant, noticing a wrong unit, knowing what your data looks like, saying "I am not sure", stopping | the parts that need the world, not the training data
:::

:::narration
An assistant is good at exactly the parts of programming that used to take the most
typing: boilerplate, library syntax, a first draft, an explanation of an error. It is
bad at the parts that need the world rather than the training data. It does not know
what you meant. It does not notice that your heights are in centimetres. It does not
know what your data looks like, and it almost never says that it is unsure. The lab
below puts you on the reading side of the loop: two functions an assistant wrote, both
of which run, one of which is wrong in each case.
:::

:::keyidea
**The brief is the design.** An assistant fills every gap in your description with the
most common interpretation. "Window-to-wall ratio" has a standard definition, but the
model may pick another one; "height" may be in metres or centimetres; "shading" may
mean an overhang or a fin. The more precisely you describe — inputs with units, outputs
with units, one worked example — the less there is to guess. Lesson 3.2 shows the
shape of a brief that leaves nothing to guess.
:::

## Read before you trust

Two functions, each written by an assistant from a one-sentence brief. Each runs. Each
is wrong. Your job is the human part of the loop: test on a case you can check by hand,
then read the line that disagrees.

:::pylab{title="Two functions the assistant wrote"}
# step: The code the assistant wrote
# Brief given to the assistant: "Write wwr(windows, walls). windows is a list of
# (width, height) in metres, walls a list of (length, height) in metres. Return the
# window-to-wall ratio." This is what came back. Run it: it works.
def wwr(windows, walls):
    """Window-to-wall ratio of a facade."""
    glazing = sum(w * h for w, h in windows)
    wall = sum(l * h for l, h in walls)
    return glazing / (wall - glazing)

print(round(wwr([(3, 2)], [(10, 3)]), 3))

# step: Test it on a case you can do by hand
# One wall 10 m x 3 m = 30 m2. One window 3 m x 2 m = 6 m2. WWR = 6 / 30 = 0.2.
result = wwr([(3, 2)], [(10, 3)])
print("got", round(result, 3), "expected 0.2")
assert abs(result - 0.2) < 1e-9, "the assistant's function disagrees with the hand calculation"

# step: Your turn - fix it
# Read the function line by line. Which line does something the brief did not ask for?
# Fix it so both tests pass.
def wwr(windows, walls):
    """Window-to-wall ratio of a facade: glazed area over gross wall area."""
    glazing = sum(w * h for w, h in windows)
    wall = sum(l * h for l, h in walls)
    return glazing / (wall - glazing)

assert abs(wwr([(3, 2)], [(10, 3)]) - 0.2) < 1e-9, "not yet - WWR is glazing over the whole wall, windows included"
assert abs(wwr([(2, 1), (2, 1)], [(8, 2.5)]) - 0.2) < 1e-9, "not yet - check the second case too"
print("Correct!")

# step: The second one - a quieter bug
import math
# Brief: "overhang_depth(window_height, sun_altitude): the horizontal overhang, in
# metres, that fully shades a window of the given height when the sun is at the
# given altitude in degrees." The assistant wrote:
def overhang_depth(window_height, sun_altitude):
    return window_height / math.tan(sun_altitude)

# Hand case: a 1.5 m window with the sun at 45 degrees needs an overhang equal to
# its height - 1.5 m - because tan(45 degrees) = 1.
print("got", round(overhang_depth(1.5, 45), 3), "expected 1.5")

# step: Your turn - fix the unit
# math.tan wants radians. The brief said degrees. Fix the function.
def overhang_depth(window_height, sun_altitude):
    return window_height / math.tan(sun_altitude)

assert abs(overhang_depth(1.5, 45) - 1.5) < 1e-6, "not yet - convert degrees to radians before tan"
assert abs(overhang_depth(2.0, 60) - 1.1547) < 1e-3, "not yet - check the 60 degree case"
print("Correct! A 0.93 m overhang would have been built from the first version.")
:::

The first function computed glazing over *opaque* wall — a real quantity, just not the
one the brief named. The second passed degrees to a function that wanted radians, and
returned 0.93 m where 1.5 m was right. Neither raised an error. Both would have been
caught in a minute by a case you can do in your head, and never by re-reading the
docstring.

:::reflect{feedback="A test is evidence about the code; the docstring is a claim by the same author."}
What is the most reliable one-minute check on a function an assistant wrote?
- Ask the assistant whether the function is correct | It will say yes, in the same confident tone it used to write the bug. It has no way to check.
- *Run it on a case whose answer you already know | Yes. Hand-calculable cases turn the function's output from generated into measured.
- Read the docstring and compare it with the brief | The docstring was written by the same model. It describes the intention, not the behaviour.
:::

:::details{summary="Show reference answer"}
The hand case is the check. Choose one where the answer is obvious — a 10 by 3 wall with a 3 by 2 window, the sun at 45 degrees — and assert it. A second case that exercises a different path (two windows, a different angle) catches the bug that the first case happened to miss. Reading the code is what you do *after* the test fails, to find the line.
:::

## The risks that come with the speed

:::cards
You cannot review what you cannot read | the reading step needs Python | Module 1 exists so that this step is available to you
"It works on the example" | one passing case proves one case | test a second case that takes a different path; test the edges
Silent unit errors | degrees and radians, metres and millimetres, kWh and kWh/m² | put the unit in every parameter name and in the brief
What you paste leaves your machine | a hosted assistant sees everything you send it | no keys, no private data, no client files in a hosted chat; a local model (3.3) sees nothing but your laptop
The model's confidence | the wrong answer is delivered in the same tone as the right one | confidence is a style, not a signal; the test is the signal
Licences | generated code can reproduce licensed code | for anything you publish, know where it came from
:::

:::narration
The speed has costs, and they are predictable. You cannot review what you cannot read,
which is why this course teaches Python before it teaches you to let a model write it.
One passing example proves one example. Units fail silently. Anything you paste into a
hosted assistant leaves your machine, so keys, private data and client files stay out
of it, or go to a local model. And the wrong answer arrives in exactly the tone of the
right one. Confidence is a style. The test is the signal.
:::

:::keyidea
**Generated code is a hypothesis about what you meant.** Running a test turns it into
evidence — [[measured]] behaviour on a case you understand. Everything in this module is
about moving code from the first category to the second before anything depends on it.
:::

:::boundary
Data | two functions written from one-sentence briefs; hand-calculable test cases
Evidence | the assistant's code is [[generated]]; each test result is [[measured]]
Establishes | that running without error does not establish correctness; that a hand case catches both the interpretation bug and the unit bug
Does not establish | how often assistants make such mistakes on real projects; that reading alone, without a test, would have caught them
:::
