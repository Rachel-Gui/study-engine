## Central question

Everyone says "agent". What is one, concretely, in code?

:::narration
This lesson begins with a simplified agent class. It stores a name, a role and
written instructions. The surrounding application sends the instructions to a
language model with the building data as context. Reading this example helps us
evaluate the instructions and distinguish them from the system that executes them.
:::

:::glossarynote
:::

The Environmental Negotiators use an {{agent}} class. This simplified excerpt
shows its three core attributes:

```python
class Agent:
    def __init__(self, name, role, instructions, color="#666", icon="bot"):
        self.name = name
        self.role = role
        self.instructions = instructions
```

:::keyidea
The excerpt stores a **name**, a **role**, and **instructions**. The `color` and
`icon` parameters are accepted but not stored in this simplified version. The
surrounding system handles model calls, tool use and coordination.
:::

## The same object, as the research literature defines it

:::narration
The class stores an agent profile; it does not implement a complete autonomous
system. Comparing it with the research definition helps clarify that distinction. Lee and colleagues, in their 2025 review of agentic A I in
the built environment, define an agent as an autonomous entity that perceives its
environment and takes actions to achieve specific objectives. And they define agentic
A I as a system that sets goals and executes tasks by using tools through reasoning.
Map that onto the code. The environment the agent perceives is the user message: the
geometry and the climate. The objective is the role and the instructions. The action
is the structured proposal it returns, which changes what the other agents and the
manager see next. And the tools come in the next lessons, when an agent is allowed to
call a simulation instead of guessing.
:::

The review by Lee et al. (2025) defines an *agent* as "an autonomous entity that
perceives its environment and takes actions to achieve specific objectives", and
*agentic AI* as "a system capable of setting goals and executing tasks to achieve
predefined objectives by utilizing various tools through reasoning". The same review
places agentic AI in a sequence: **perception AI** interprets images, text and sound;
**generative AI** creates content (Module 2); **agentic AI** sets goals, reasons, uses
tools and acts; **physical AI** puts that cognition into robots.

:::figure{id=agentic_framework caption="Figure 1. Where agentic AI sits, and how the built-environment literature classifies it — by application, by functional role on the data–information–knowledge–wisdom ladder, and by learning approach. Original diagram after Lee et al. (2025)."}
:::

:::cards
Perceives its environment | the user message: geometry, climate, the other agents' arguments | what the model is given to read
Achieves specific objectives | the role and the instructions | what the model is told to want
Takes actions | a structured proposal that changes the shared state | what the next agent or the manager reads
Uses tools through reasoning | a simulation or a retrieval call the agent may make — Lessons 4.2 and 4.5 | what turns an opinion into a checked one
:::

Three things follow from the classification in Figure 1. First, the Environmental
Negotiators are one small point in a larger space: the review's five application areas
are BIM, building performance simulation, building management systems, building
digital twins and urban-scale planning, and the Negotiators sit in the second, at the
early-design end. Second, the review sorts what agents *do* on the DIKW ladder, from
interpreting data to supporting decisions — and the destination is decision
**support**. Its own definition of an "agentic built environment" is one in which
agents "interact, collaborate, and co-evolve with human stakeholders"; nothing in it
removes the designer from the decision, which is the thread Lesson 2.10 started.
Third, of the four learning approaches the review identifies — prompt engineering,
zero-shot, few-shot and fine-tuning — everything in this module uses the first. No
model is trained here; the behaviour of an agent is written, in words, which is why
the rest of this lesson is about reading prompts.

## How an agent becomes an API call

:::narration
So how do those fields turn into an actual request? Two pieces. Your instructions
become the system prompt, with an output schema appended so the model returns
structured data instead of prose. The building geometry and the climate data become
the user message. The model reads both and returns J S O N. That is the entire A I
call. Many frameworks support this request pattern, though their APIs and agent
capabilities differ.
:::

:::figure{id=agent_anatomy caption="Figure 2. Agent fields become a system prompt; your data becomes the user message. Redrawn for this module."}
:::

```
system prompt  =  your agent's instructions  +  output schema
user message   =  building geometry data     +  climate data
```

The call itself is one line:

```python
response = await client.chat(model=MODEL, messages=messages)
```

:::keyidea
**system prompt + user context → model → structured response.** This is the request pattern used in this lesson.
Agent frameworks may also manage memory, tool calls and multi-step execution.
:::

## Read the prompt, not the framework

:::narration
Here is the widget I want you to spend time with. On the left you can switch between
a vague set of instructions and a sharp one. On the right you see exactly what the
model receives in each case. The building data is identical either way. The only
thing that changes is how much you constrained the answer. Read both versions and
notice what the sharp one does: it scopes the agent to one concern, gives it a
checklist of angles, forbids it from wandering into other agents' territory, and
forces it to produce a number rather than a hedge.
:::

:::widget{id=prompt-lab}
:::

:::compare
Vague instructions | "Comment on the building's energy performance." | May produce general commentary without the evidence or specificity needed for a design decision.
Sharp instructions | "Your ONLY concern is... propose a specific lower number... you may NOT consider daylight." | Specifies a scope, a checklist, boundaries and a concrete output. These instructions make the expected response easier to assess.
:::

Four moves make the difference, and they transfer to any agent you ever write:

:::cards
Scope it | "Your ONLY concern is..." | unfocused agents produce generic output
Give a checklist | bullet-point angles to argue from | without structure, the model rambles
Force a commitment | "propose a specific lower number" | concrete output instead of hedging
Draw boundaries | "You may NOT consider..." | overlap between agents weakens the debate
:::

## Try it yourself

:::narration
This lab runs entirely in your browser with no model behind it, and that is
deliberate. It assembles the exact request your agent definition would produce, so
you can read it before you spend a single token. Edit the instructions, run it again,
and watch the assembled prompt change. The checklist at the end is a crude heuristic,
not a judge, but it catches the four failures we just listed.
:::

:::pylab{title="Assemble the prompt your agent would send"}
# step: Define an agent and assemble its request
class Agent:
    def __init__(self, name, role, instructions):
        self.name, self.role, self.instructions = name, role, instructions

SCHEMA = '\n\nRespond ONLY with JSON: {"argument": str, "critical_finding": str}'

CONTEXT = """## Geometry
A 6-storey block, 42 x 24 m, WWR 0.55, oriented 15 deg east of south.

## Climate
Seattle WA, ASHRAE 4C, heating-dominated."""

# ---- EDIT THIS ------------------------------------------------------------
my_agent = Agent(
    name="Energy Efficiency Advocate",
    role="Argue for minimal operational energy use",
    instructions="""You are the energy efficiency advocate. Your ONLY concern
is reducing operational energy use.

Argue from these angles:
- Is the surface-to-volume ratio efficient for this climate?
- Is the WWR causing excessive heat loss?

Reference specific numbers. If the WWR is too high for a heating-dominated
climate, say so and propose a specific lower number.

You may NOT consider daylight quality or embodied carbon.""",
)
# ---------------------------------------------------------------------------

print("=" * 68); print("SYSTEM PROMPT"); print("=" * 68)
print(my_agent.instructions + SCHEMA)
print(); print("=" * 68); print("USER MESSAGE"); print("=" * 68)
print(CONTEXT)

# step: A crude check on the four moves
text = my_agent.instructions
checks = {
    "scoped ('only' / 'your job is')": any(w in text.lower() for w in ("only", "your job")),
    "gives a checklist (bullet points)": text.count("-") >= 2,
    "forces a number ('specific' / digits)": ("specific" in text.lower()
                                              or any(c.isdigit() for c in text)),
    "draws boundaries ('may not' / 'do not')": any(w in text.lower()
                                                   for w in ("may not", "do not", "not consider")),
}
for k, v in checks.items():
    print(f"  {'yes' if v else 'NO '}   {k}")
print(f"\n  {sum(checks.values())} of 4. This is a keyword heuristic, not a judge —")
print("  it catches the obvious failures, it cannot tell you if the content is right.")
:::

:::reflect
An advocate returns a fluent paragraph that never mentions a single number from the
geometry. What is the most likely cause?
- The model is too small for the task
- *The instructions never asked it to reference specific numbers or commit to a value
- The geometry data was not passed in the user message
:::
