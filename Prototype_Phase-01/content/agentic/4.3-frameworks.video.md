:::scene{type=title}
narration: |
  Welcome to lesson four point three, choosing a framework. There are six sensible
  ways to wire an agent to a design tool, from raw Python to a Grasshopper plug in.
  None of them is best. Each one buys something at the cost of something else, and
  this lesson gives you the two axes that make the choice, plus the one piece of
  plumbing, M C P, that keeps appearing everywhere.
:::

:::scene{type=diagram id=framework_landscape}
heading: Six options on two axes
narration: |
  Here is the landscape. Across the bottom, how much programming background an option
  needs. Up the side, how directly the agent reaches the C A D environment. Watch where
  the six land. Raw Python with the OpenAI S D K teaches the agent loop fast, but
  touches no geometry. Grasshopper with a plug in shows geometry moving with almost no
  code, but gives you no handoffs between agents. Almost every option buys one axis at
  the cost of the other.
:::

:::scene{type=cards}
heading: The six, in one line each
items:
  - title: 01 · OpenAI SDK + Python
    text: Fast, concentrated learning of the loop. No CAD, needs programming.
  - title: 02 · SDK inside Grasshopper
    text: Teachable with little coding. Simulation plug-ins are hard; needs the Rhino 9 preview.
  - title: 03 · FastMCP + any chat UI
    text: Real depth on MCP; test in any chat client. No CAD, no handoffs.
  - title: 06 · Grasshopper + Swiftlet
    text: CAD access with instant visual feedback and no code. No handoffs or swarm behaviour.
narration: |
  In one line each. Option one, the OpenAI S D K in raw Python: fast, concentrated
  learning of the agent loop; no C A D, needs programming. Option two, the S D K inside
  Grasshopper: teachable with little coding; simulation plug ins are hard. Option three,
  Fast M C P with any chat interface: real depth on M C P, testable in any chat client;
  no C A D. Options four and five add Rhino Compute and a deployed app, scaling far at
  the cost of advanced programming. And option six, Grasshopper plus Swiftlet: C A D
  access with instant visual feedback and no code; no handoffs between agents.
:::

:::scene{type=idea icon=bulb}
text: MCP — a standard way for a model / to discover and call the tools you host.
sub: You write small functions. The model sees the list and chooses. The same server then works with any client that speaks the protocol.
narration: |
  M C P keeps appearing in that list, so here is what it is. The Model Context Protocol
  is a standard way for a model to discover and call tools you host. You write small,
  single purpose functions: compute the surface to volume ratio, fetch the climate
  data. The model sees the list of tools and chooses which to call. And because it is a
  standard, the same server works with any client that speaks the protocol: a chat
  app, a coding agent, your own script.
:::

:::scene{type=steps}
heading: An MCP server, in four steps
steps:
  - Write the server — small functions, FastMCP
  - Inspect it — see every tool the model will see
  - Expose it — a tunnel, and the /mcp suffix on the URL
  - "*Connect a client — any chat app that speaks MCP"
narration: |
  Four steps to a working server. Write it: small functions with Fast M C P. Inspect
  it: the inspector shows you every tool exactly as the model will see it, and if a
  description is vague to you, it is vague to the model. Expose it through a tunnel,
  and remember the slash m c p suffix on the U R L: the bare tunnel address is not the
  endpoint, and that suffix is the step people miss. Then connect a client: any chat
  app that speaks the protocol.
:::

:::scene{type=idea icon=warn}
