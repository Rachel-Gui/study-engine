:::scene{type=diagram id=agentic_framework}
heading: What the research literature calls an agent
points:
  - Perceives its environment — the user message, geometry and climate
  - Achieves specific objectives — the role and the instructions
  - Takes actions — a structured proposal the next agent reads
  - Uses tools through reasoning — a simulation call, in Lessons 4.2 and 4.5
narration: |
  Hold that next to the definition the research literature uses. A 2025 review of
  agentic A I in the built environment, by Lee and colleagues, defines an agent as an
  autonomous entity that perceives its environment and takes actions to achieve
  specific objectives, and agentic A I as a system that sets goals and executes tasks
  by using tools through reasoning. It sits in a sequence: perception A I interprets,
  generative A I creates, agentic A I acts, physical A I puts that into robots. Now map
  the definition onto the profile and its surrounding system. The environment the agent perceives is the
  user message: the geometry and the climate. The objective is the role and the
  instructions. The action is the structured proposal it returns, which changes what
  the next agent sees. And the tools come in the next lessons, when an agent may call a
  simulation instead of guessing. The review classifies agents three ways: by
  application, where the Negotiators sit in building performance simulation; by role,
  from interpreting data up to supporting decisions; and by learning approach, and
  everything in this module uses the first one, prompt engineering. Nothing is trained.
  The behaviour is written in words, which is why this lesson is about reading prompts.
:::

:::scene{type=diagram id=agent_anatomy}
heading: How an agent becomes one API call
narration: |
  Watch how the agent becomes a call. The agent's instructions, plus a description of
  the output shape you want, become the system prompt. Your data, the building geometry
  and the climate, become the user message. Both go to the model. And the model returns
  a structured response. System prompt plus user context, into the model, out comes a
  structured answer. Many frameworks support this request pattern, though their APIs and
  agent capabilities differ.
:::

:::scene{type=code}
heading: The call itself is one line
code: |
  reply = ollama.chat(model="llama3.1", messages=[
      {"role": "system", "content": agent.instructions + OUTPUT_SCHEMA},
      {"role": "user",   "content": geometry_and_climate_json},
  ])
output: |
  {"concern": "WWR of 0.55 in a heating-dominated climate",
   "proposed_wwr": 0.35, "reasoning": "..."}
note: The same call you made in Lesson 2.9 — with the agent's instructions as the system prompt and your data as the user message.
narration: |
  And the call itself is one line. It is the same call you made in lesson two point
  nine: a model, a system message, a user message. The agent's instructions are the
  system message. Your data is the user message. The reply comes back as JSON with a
  concern, a proposed number, and the reasoning. If you can read this, you can read
  the source code of any agent framework.
:::

:::scene{type=compare}
heading: Read the prompt, not the framework
left:
  title: Vague instructions
  points:
    - '"Comment on the building''s energy performance."'
    - Fluent, general, useless for a decision
    - Nothing constrains the answer
right:
  title: Sharp instructions
  points:
    - '"Your ONLY concern is operational energy."'
    - Angles to argue from, as a checklist
    - '"Propose a specific lower number."'
verdict: The behaviour of an agent is in its prompt. Change the prompt and you change the agent.
narration: |
  So where does an agent's behaviour live? In its prompt. Give it vague instructions,
  comment on the building's energy performance, and you get something fluent, general
  and useless for a design decision. Give it sharp instructions, your only concern is
  operational energy, here are the angles to argue from, propose a specific lower
  number, and you get an argument you can act on. Read the prompt, not the framework.
  Change the prompt and you change the agent.
:::

:::scene{type=cards}
heading: Four moves that transfer to any agent you write
items:
  - title: Scope it
    text: '"Your ONLY concern is..." Unfocused agents produce generic output.'
    tag: 1
  - title: Give a checklist
    text: Bullet-point angles to argue from. Without structure, the model rambles.
    tag: 2
  - title: Force a commitment
    text: '"Propose a specific lower number." No number, no decision.'
    tag: 3
  - title: Fix the output shape
    text: Ask for JSON with named fields, so the next agent can read it.
    tag: 4
narration: |
  Four moves make the difference, and they transfer to every agent you will ever write.
  Scope it: your only concern is. Unfocused agents produce generic output. Give a
  checklist: bullet point angles to argue from, because without structure the model
  rambles. Force a commitment: propose a specific lower number, because no number means
  no decision. And fix the output shape: ask for JSON with named fields, so the next
  agent in the pipeline can read it.
:::
