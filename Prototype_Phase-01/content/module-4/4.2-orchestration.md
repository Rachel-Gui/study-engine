## Central question

Once you have several agents, what decides the order they run in?

:::narration
A single agent is a prompt. A system of agents is a set of decisions about
dependency: what has to finish before what else can start, and what can safely happen
at the same time. In the Environmental Negotiators workshop the pipeline runs in three
phases. The site researcher goes first and alone, because every other agent needs its
climate data. The advocates then run in parallel, because none of them reads any
other's output. The manager runs last, because it needs all of them. Gather context,
fan out, synthesise. You will make the same three decisions in any agent system you
build.
:::

:::figure{id=orchestration caption="Figure 1. The three-phase pipeline: sequential, parallel, sequential. Redrawn for this module."}
:::

```
Phase 1:  Site Researcher runs alone       sequential — everyone needs its data
Phase 2:  Advocates run in parallel        independent — they don't see each other
Phase 3:  Manager runs last                sequential — it needs all advocate results
```

:::keyidea
**Gather context → parallel independent work → synthesise.** Dependency, not speed, is
what sets the shape. Two agents can run at once exactly when neither reads the other's
output.
:::

## What the shape costs you

:::narration
Move the sliders. Adding advocates costs you almost nothing in wall-clock time while
they run in parallel, because they all wait on the same one call. Switch them to run
one after another and the cost becomes linear in the number of agents. That is the
practical argument for parallelism. But notice what you cannot parallelise away: the
researcher at the start and the manager at the end are fixed costs, because the
dependency is real.
:::

## Why the advocates must not see each other

:::narration
There is a design reason the advocates are isolated, and it is not performance. If
each advocate could read the others, they would converge. Models are agreeable. The
second one to speak would soften its position to accommodate the first, and you would
end up with a committee report instead of a disagreement. The value of a multi-agent
system comes from structured disagreement, not consensus. Isolate them so each
argues its corner honestly, then let one agent whose explicit job is arbitration do
the reconciling.
:::

:::keyidea
Value comes from **structured disagreement**, not consensus. Let advocates see each
other and they converge — models are agreeable. Isolate them, then give one agent the
explicit job of resolving conflict.
:::

Real tradeoffs to build tension around:

:::compare
Daylight vs Energy | more glass vs less glass | The classic conflict. Neither is wrong; the manager has to pick and say what it sacrificed.
Carbon vs Comfort | compact form vs generous floor plates | Embodied carbon rewards compactness; occupant experience often does not.
:::

## The manager's job is deciding, not summarising

:::narration
The most common failure when people write their first manager agent is that they ask
it to summarise. It will oblige, and you will get a paragraph that says every advocate
raised valid points. That is useless. The manager instruction in the workshop does
four specific things instead: list the agreements, name each conflict with each
advocate's proposed number, make a decision without averaging, and state what was
sacrificed and why. The last clause is the one that matters. A building that is
mediocre at everything is worse than one that excels at two things and consciously
accepts a tradeoff on the third.
:::

:::workflow
List agreements | Where did everyone align? These are the easy wins, and naming them clears the ground. | 
Name each conflict | State the specific issue and each advocate's position, with their proposed number. | 
Decide, do not average | Choose the position that best serves overall performance. Averaging produces a design nobody argued for. | 
Say what you sacrificed | And why. A tradeoff that is not named is a tradeoff nobody can review. | 
Emit a constraint packet | Numeric bounds a parametric model can actually consume: max_wwr_east, target_wwr_south, max_sv_ratio. | 
:::

:::keyidea
"Do NOT average." An averaged answer is a design no advocate argued for and no
reviewer can trace. Make the model choose, and make it explain the loss.
:::

:::reflect
You add a fourth advocate and the manager's verdict becomes noticeably blander. What
is the most likely explanation?
- The model ran out of context
- *The new advocate overlaps with an existing one, so there is less real disagreement to resolve
- Four agents is too many for the pattern
:::
