## What you are building

:::narration
This is the hands-on session. You will write A I agents that debate a building's
design. Each advocate argues from exactly one environmental perspective, energy,
daylight, carbon, resilience, and a manager agent resolves the conflicts and proposes
a final massing. You work in one file, in plain English. No coding experience is
needed, because writing an agent is writing instructions, and you already know how to
do that.
:::

You will create agents that debate building design decisions. Each argues from a
single environmental perspective; a manager resolves the conflicts and proposes a
final design. **You work in one file, `negotiators.py`, in plain English.**

:::stats
1 file | negotiators.py, the only one you edit
2+ | advocates you write
3 | phases in the pipeline
:::

:::flow
Site Researcher > your advocates in parallel > Manager arbitrates > suggested geometry > Apply to sliders
:::

## Before the session

:::narration
Get this done before the workshop starts, not during it. The stack is Ollama for the
model, Python three point ten or newer, and Node eighteen or newer for the dashboard.
Ollama runs the model on your own machine, which means no A P I key and no per-token
cost, and it also means the model is smaller than a hosted one. Expect it to be
literal about instructions. That is useful for learning: a small model punishes vague
prompts immediately.
:::

:::workflow
Install Ollama | Then sign in and pull the workshop model. Ollama runs the model locally — no API key, no per-token cost. | 
Install Python 3.10+ | Then `pip install -r requirements.txt` from the `negotiators/` folder. | 
Install Node 18+ | Then install the frontend dependencies. The dashboard is a Vite app. | 
Run the verifier | `python verify.py` checks every piece before the session rather than during it. | 
:::

:::keyidea
Full instructions are in `SETUP.md` inside the workshop folder. Run `verify.py` the
day before, not on the morning of. Every minute spent installing is a minute not spent
writing agents.
:::

## Write your advocates

:::narration
Now the part that matters. Find the empty advocates list in negotiators dot pie and
add your first agent. Pick one environmental perspective and argue it hard. Then add a
second agent that will disagree with the first, because that is the whole design
principle here: value comes from structured disagreement, not consensus. Daylight
wants more glass and energy wants less. Carbon wants compact forms and comfort wants
generous floor plates. Resilience wants conservative design and cost wants minimal
material. Pick a real tension and build it.
:::

```python
advocates = [
    Agent(
        name="Energy Efficiency Advocate",
        role="Argue for minimal operational energy use",
        instructions="""You are the energy efficiency advocate. Your ONLY concern
        is reducing the building's operational energy consumption.

        Look at the geometry and climate data provided. Argue from these angles:
        - Is the surface-to-volume ratio efficient for the climate?
        - Is the WWR too high, causing excessive heat loss or cooling load?
        - Does the orientation take advantage of passive solar heating?

        Reference specific numbers from the data. Take a strong position.
        If the WWR is too high for a heating-dominated climate, say so and
        propose a specific lower number.

        You may NOT consider daylight quality or embodied carbon. Those are
        other advocates' concerns.""",
        color="#3B82F6",
        icon="zap",
    ),
]
```

`color` takes any hex code. `icon` is one of `globe`, `sun`, `leaf`, `zap`, `users`,
`bot`.

:::keyidea
Write the second advocate to **conflict** with the first. If both want the same thing,
the manager has nothing to arbitrate and you have built a very slow summariser.
:::

## Run, read, iterate

:::narration
Save the file and the dashboard picks up your agents within a few seconds. But saving
does not start a debate. You have to click Quick Debate or Full Debate each time. Then
read the results properly. On each advocate card, ask whether it argued what you
expected, and if it did not, the fix is almost always in your instructions rather than
in the model. On the manager card, look for the conflicts section and what it says it
sacrificed. Then click Apply, which pushes the manager's geometry back into the
sliders, and debate again. The agents are now arguing about the manager's proposal.
Watch whether they change their minds.
:::

:::workflow
Save and check | The header should show your agent count — "4 agents online" with two advocates. Saving alone starts nothing. | 
Click Debate | Quick or Full. You click it every time; the file watcher only reloads definitions. | 
Read the advocates | Did each argue what you expected? If not, the fix is in your instructions, not the model. | 
Read the manager | Agreements, conflicts, what it sacrificed and why, and the suggested geometry. | 
Apply and re-debate | The agents now argue about the manager's proposal. Do they change position? | 
Change the site | Try a desert city, then a coastal one. Watch which arguments survive the move. | 
:::

## What you actually built

:::narration
Step back at the end and name the pattern, because the pattern is the transferable
part. An agent definition is a system prompt. Context injection is any structured data
passed as the user message. The output schema is a response-format specification.
Orchestration is your dependency graph. And prompt quality is the single biggest lever
in the whole system. The frameworks will change. OpenAI Assistants, Claude, LangChain,
CrewAI, whatever arrives next year. That table does not change.
:::

| Concept | In this workshop | In any agent system |
|---|---|---|
| Agent definition | `Agent(name, role, instructions)` | A system prompt sent to an LLM API |
| Context injection | Geometry + climate as user message | Any structured data passed to the model |
| Output schema | JSON format appended to instructions | Response-format specification |
| Orchestration | Research → parallel advocates → manager | Sequential dependencies, parallel fan-out, aggregation |
| Prompt quality | Specific, opinionated, bounded | The single biggest lever in any AI system |

## What this workshop establishes, and what it does not

:::narration
Finally, the boundary, because this module needs one as much as the others do. The
agents are language models reasoning over the numbers you handed them. Nothing here
ran an energy simulation. When an advocate says a window-to-wall ratio is too high for
this climate, that is a plausible argument from a model that has read a great deal
about building energy. It is not a result. The output of this system is a structured
set of design questions and a constraint packet, and both of those need to go into a
real simulation before anybody builds anything.
:::

:::keyidea
**No simulation runs anywhere in this workshop.** The advocates reason over numbers you
supplied. Their arguments are hypotheses to test, not performance results.
:::

- **What it establishes** — a structured set of design tensions, made explicit, with a
  named tradeoff and a numeric constraint packet.
- **What it does not** — any energy, daylight, or carbon quantity. No {{uncertainty}}
  is attached to anything an agent says.
- **Known failure conditions** — a local model will state confident numbers it cannot
  support. Two advocates with overlapping scopes produce a bland verdict. An
  unconstrained manager summarises instead of deciding.
- **Where it goes next** — feed the constraint packet into the Module 2 and 3 models,
  or into a real simulation. That is where a number becomes a result.

:::keyidea
Course rule, unchanged here: a model learns patterns in its training data. It does not
establish causation, guarantee code compliance, or replace a licensed professional's
judgment. See **Accuracy boundaries** in the Reference section.
:::

:::reflect
An advocate states that reducing WWR to 0.28 will cut annual energy use by 14%. What is
that number?
- A prediction, accurate to roughly the stated precision
- *An unverified claim from a language model — no simulation ran, so it needs testing before use
- A result, since it came from an agent given real geometry and climate data
:::
