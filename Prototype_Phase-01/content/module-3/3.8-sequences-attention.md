## Central question

Episode 3.7 treated every ten-minute reading as an independent row. What changes
when the model is allowed to see the readings before it?

:::narration
Episode three point seven fitted a network to one house, one row per ten minutes,
and the honest score on a chronological split was poor. This episode asks why, and
the answer is embarrassing in a useful way. Every row was treated as if it had no
past. But appliance load at seven in the evening depends enormously on the load at
six fifty. The order of the rows is information, and the model was never shown it.
Three families of model can see the past: a sliding window, a recurrent network, and
attention. You will use the first on the real data and watch a single lag feature
outperform twenty-eight sensors, and then take the third apart in a widget.
:::

:::figure{id=sequence_models caption="Figure 1. Three ways to let a model see the past. Redrawn for this module."}
:::

:::flow
Independent rows > A window of recent rows > A state carried through time > Attention over the whole history
:::

By the end of this episode you should be able to:

- Build lag features and say why they must come from the past only
- Beat the persistence baseline, and explain why it is the baseline
- Describe what an RNN carries and what attention computes
- Read attention weights and say what the model looked at

## The persistence baseline

:::narration
Before any sequence model, the baseline. Predict that the next ten minutes will look
exactly like the last ten. That is called persistence, and on the appliance data it
scores an R squared of about point four seven on the chronological test period. Read
that against Episode three point seven: a neural network with twenty-eight sensors
and clock features scored lower on the same split. A model that cannot beat "nothing
changes" has not learned anything about time. Every sequence result in the
literature should be read against this number, and many are not.
:::

:::keyidea
**Persistence**: ŷ(t) = y(t − 1). On the appliance data it reaches R² ≈ 0.47 on a
chronological test period. Any sequence model that cannot beat it has learned
nothing about time.
:::

:::compare
Sensors + clock, chronological | R² ≈ 0.13 | Twenty-eight measured channels and the time of day. The present alone barely predicts the next ten minutes.
+ one lag feature | R² ≈ 0.54 | Add the previous reading as a feature. One number outperforms twenty-eight sensors. The signal is in the sequence.
:::

## Sliding windows: the recent past as features

:::narration
The simplest sequence model is not a new architecture. Take the last k readings and
lay them out as k extra columns: the reading one step ago, two steps ago, six steps
ago, the mean of the last hour. Then any model from Module two or three can use
them. Two rules. The features must come strictly from the past, never from the
future, or you have leaked the answer. And the split must be chronological, because
a window contains its neighbours by construction, so a random split is leakage in
its purest form. Run the lab and watch what one lag column does to the score.
:::

:::keyidea
Lag features must be built from the past only: `shift(1)`, never `shift(−1)`. And with
windows, a random split is not merely optimistic — every test row's window overlaps a
training row's window. Chronological, always.
:::

:::predict
You add the *next* reading as a feature by mistake — `shift(−1)` instead of
`shift(1)` — and the model scores R² 0.99 on the test period. What happened?
- The model found a strong physical relationship | Nothing physical predicts the next ten minutes that well.
- *The feature contains the answer; it is leakage from the future | Yes. A score that good on this data is a bug until proven otherwise.
- Sensor data is easier than it looked | It is not. Persistence scores 0.47.
:::

## Interactive code lab — lag features on the real data

:::narration
The lab loads the same nineteen thousand ten-minute rows as Episode three point
seven, keeps them in time order, and scores three things on the last twenty percent:
persistence, the sensors and clock alone, and the sensors plus lag features. Ridge
regression is used throughout so it runs in a second; the point is the features, not
the model. The last step plots two days of the test period. The model tracks the
daily rhythm and lags the spikes, because nothing in the past tells it a kettle is
about to go on. That lag is what a sequence model can and cannot do.
:::

:::pylab{title="Persistence, lags, and the chronological split" packages=numpy,pandas,scikit-learn,matplotlib}
# step: Load the ten-minute readings and keep time in order
import pandas as pd, numpy as np
from pyodide.http import open_url

URL = ("https://raw.githubusercontent.com/LuisM78/"
       "Appliances-energy-prediction-data/master/energydata_complete.csv")
df = pd.read_csv(open_url(URL), parse_dates=["date"]).sort_values("date").reset_index(drop=True)

df["hour"] = df.date.dt.hour + df.date.dt.minute / 60
df["hour_sin"], df["hour_cos"] = np.sin(2 * np.pi * df.hour / 24), np.cos(2 * np.pi * df.hour / 24)
df["weekday"] = (df.date.dt.weekday < 5).astype(int)
print("rows:", len(df), " from", df.date.min(), "to", df.date.max())
print("Every row is 10 minutes after the previous one. That order is the whole point of this lab.")

# step: The simplest sequence model - persistence
from sklearn.metrics import r2_score, mean_absolute_error
y = df.Appliances.values
cut = int(0.8 * len(df))                        # chronological: train on the past, test on the future
naive = df.Appliances.shift(1).values           # "the next ten minutes look like the last ten"
print("persistence (predict the previous reading):")
print("   R2  =", round(r2_score(y[cut:], naive[cut:]), 3),
      "  MAE =", round(mean_absolute_error(y[cut:], naive[cut:]), 1), "Wh")
print("Any sequence model has to beat this number, or it has learned nothing about time.")

# step: Sensors and clock only - what Episode 3.7 used
from sklearn.linear_model import Ridge
from sklearn.preprocessing import StandardScaler
sensors = [c for c in df.columns if c.startswith(("T", "RH_"))] + ["Press_mm_hg", "Windspeed", "Visibility"]
base = sensors + ["hour_sin", "hour_cos", "weekday", "lights"]

def chrono_score(cols):
    X = df[cols].values
    ok = ~np.isnan(X).any(1)
    Xtr, Xte = X[:cut][ok[:cut]], X[cut:][ok[cut:]]
    sc = StandardScaler().fit(Xtr)
    m = Ridge(1.0).fit(sc.transform(Xtr), y[:cut][ok[:cut]])
    p = m.predict(sc.transform(Xte))
    return r2_score(y[cut:][ok[cut:]], p), mean_absolute_error(y[cut:][ok[cut:]], p)

r, mae = chrono_score(base)
print(f"sensors + clock, chronological split:   R2 = {r:.3f}   MAE = {mae:.1f} Wh")
print("The present alone barely predicts the next ten minutes. Now give the model the past.")

# step: Sliding window - the recent past as features
for k in (1, 2, 3, 6):
    df[f"lag{k}"] = df.Appliances.shift(k)          # the reading k steps ago
df["last_hour_mean"] = df.Appliances.shift(1).rolling(6).mean()

print(f"{'features':40s} {'R2':>7s} {'MAE':>8s}")
for label, cols in [("sensors + clock", base),
                    ("+ previous reading (lag 1)", base + ["lag1"]),
                    ("+ lags 1, 2, 3, 6", base + ["lag1", "lag2", "lag3", "lag6"]),
                    ("+ lags + last-hour mean", base + ["lag1", "lag2", "lag3", "lag6", "last_hour_mean"]),
                    ("lags + clock only, no sensors", ["lag1", "lag2", "lag3", "lag6", "last_hour_mean", "hour_sin", "hour_cos"])]:
    r, mae = chrono_score(cols)
    print(f"{label:40s} {r:7.3f} {mae:8.1f}")
print("\nOne lag feature does more than 28 sensors. The signal is in the sequence, not the snapshot.")

# step: Look at two days of predictions
import matplotlib.pyplot as plt
cols = base + ["lag1", "lag2", "lag3", "lag6", "last_hour_mean"]
X = df[cols].values; ok = ~np.isnan(X).any(1)
sc = StandardScaler().fit(X[:cut][ok[:cut]])
m = Ridge(1.0).fit(sc.transform(X[:cut][ok[:cut]]), y[:cut][ok[:cut]])
seg = slice(cut + 600, cut + 600 + 288)          # 288 rows = 2 days
plt.figure(figsize=(7.5, 3))
plt.plot(df.date[seg], y[seg], c="k", lw=1, label="measured")
plt.plot(df.date[seg], m.predict(sc.transform(X[seg])), c="#4b2e83", lw=1.2, label="sliding-window model")
plt.ylabel("Wh per 10 min"); plt.legend(); plt.title("Two days of the test period")
plt.xticks(rotation=30); plt.tight_layout()
print("The model tracks the daily rhythm and lags the spikes: it cannot know a kettle is about to go on.")
:::

:::keyidea
The sensors are not useless — they are the wrong *kind* of information for a
ten-minute-ahead question. For a day-ahead question, or for a model of *why* load
happens, they matter again. Match the features to the horizon.
:::

## Recurrent networks: a state carried through time

:::narration
A window has a fixed length. A recurrent network removes that limit by carrying a
state: at each step it reads the new input and its own previous state, and produces
a new state. In principle that state can remember anything from the whole history.
In practice, plain recurrent networks forget quickly, because the gradient has to
travel back through every step and it shrinks or explodes on the way. The L S T M,
from nineteen ninety-seven, fixed that with gates that decide what to keep and what
to discard, and it dominated sequence modelling for twenty years. Its cost is that
it is sequential: step t cannot start until step t minus one is finished.
:::

:::cards
RNN | h(t) = φ(W·[x(t), h(t−1)]) | a state, updated every step; forgets over long ranges
LSTM / GRU | gated state | learns what to keep and what to drop; the workhorse for building time series
1D CNN | kernels over time | the sliding window learned end to end; fast and often enough
Transformer | attention over every past step | parallel, long-range, inspectable weights; hungry for data
:::

:::compare
Sliding window + MLP | fixed memory, any tabular model | Cheap, robust, and on the appliance data hard to beat. Start here.
LSTM | learned memory of unbounded length | Wins when the relevant past is far away or of varying length: a heating cycle, a weekly pattern, a fault that develops over days.
:::

## Attention: weigh the past, then sum it

:::narration
Attention replaces the carried state with a direct look at every past step. For each
past reading the model computes a score against a query, "what matters for
predicting now", turns the scores into weights that sum to one with a softmax, and
returns the weighted sum of the readings. Three things follow. It is parallel: every
step is scored at once. It is long-range: a reading from yesterday is as reachable as
one from ten minutes ago. And it is inspectable: after the fact, you can read the
weights and say what the model looked at. The widget makes the two ingredients of
the score into sliders so you can see the mechanism before any of it is learned.
:::

:::figure{id=attention caption="Figure 2. Scores become weights, weights sum to one, the prediction is a weighted sum of the past. Redrawn for this module."}
:::

:::widget{id=attention-lab}
:::

:::keyidea
α = softmax(q·kᵢ / √d), ŷ = Σ αᵢ vᵢ. The weights are learned, they sum to one, and you can
read them afterwards. That last property is why attention is worth its cost in an
engineering setting: the model can show what it looked at.
:::

:::technical{summary="Queries, keys, values — and what the Transformer adds"}
For a sequence of vectors xᵢ, three learned projections produce a query q = W_q x,
keys kᵢ = W_k xᵢ and values vᵢ = W_v xᵢ. The output is Σ softmax(q·kᵢ/√d) vᵢ. Several
such heads run in parallel (multi-head attention), each free to look for a different
pattern — one head for "same time yesterday", one for "the last hour". Because
attention has no notion of order on its own, the position of each step is added to
its vector (positional encoding). Stack attention with small feed-forward layers and
you have a Transformer (Vaswani et al., 2017). For building time series the practical
advice is unchanged: it needs far more data than a window model, so establish the
baseline first.
:::

:::predict
In the widget, set sharpness very low. What happens to the prediction?
- It becomes more accurate; the model uses more of the past | Using all of it equally is not the same as using it well.
- *It approaches the 24-hour mean, whatever the query | Yes. Low sharpness flattens the softmax to near-uniform weights, and a uniform weighted sum is the mean.
- It fails because the weights no longer sum to one | Softmax weights always sum to one, at any temperature.
:::

## Architectural applications and the boundary

:::narration
Where sequence models are used on buildings: short-horizon load forecasting for
control, fault detection from the shape of a sensor trace, occupancy inference,
predictive maintenance, and in research, city-scale demand response. The boundary is
the same as everywhere in this module. A model trained on one house's winter is a
model of that house's winter. The persistence baseline is not optional. And the
chronological split is not a preference; with windowed data it is the only split
that measures anything.
:::

- Short-horizon load and indoor-temperature forecasting for control.
- Fault detection from the shape of a sensor trace over hours or days.
- Occupancy inference from CO₂, motion and plug-load sequences.
- Predictive maintenance of HVAC equipment from vibration or cycling patterns.
- Day-ahead demand forecasting for grid interaction and demand response.

:::boundary
Data | one occupied house near Mons, Belgium, January–May 2016, ten-minute readings ([[measured]]); the attention widget uses an illustrative synthetic day
Split | chronological: first 80% of the period to train, last 20% to test
Evidence | lab scores are [[measured]] on real data with a linear model; they are a floor for sequence models on this house, not a ceiling
Establishes | that the recent past carries most of the ten-minute-ahead signal, that persistence is the baseline, what attention computes
Does not establish | that an LSTM or Transformer beats the window model here — untested in this episode — or that any of it transfers to another building or season
:::

:::reflect
A paper reports an LSTM forecasting building load with R² 0.93 and does not mention
persistence. What should you ask first?
- Which optimiser was used | Rarely the reason a sequence model succeeds or fails.
- *What persistence scores on the same split — and whether the split was chronological | Yes. Both questions decide whether 0.93 means anything.
- How many layers the LSTM had | Depth does not answer whether the baseline was beaten.
:::
