## About the dataset

:::narration
Episode two point six fitted a linear model to a hundred and twenty one U W buildings,
one row per building, one number per year. This episode goes to the other extreme:
one house, sampled every ten minutes for four and a half months. Nineteen thousand
seven hundred and thirty five rows of real measurement from a Zigbee sensor network in
an occupied low-energy house near Mons in Belgium, merged with weather from Chievres
airport. Nothing here is simulated, so nothing here is tidy, and that is the point.
This is where a linear model stops being enough.
:::

The [Appliances Energy Prediction](https://www.kaggle.com/datasets/loveall/appliances-energy-prediction)
dataset (Candanedo, Feldheim & Deramaix, 2017) is **real measurement**, not
simulation. Temperature and humidity come from a ZigBee network in nine rooms;
outdoor conditions come from the weather station at Chièvres airport.

:::stats
19,735 | ten-minute readings
28 | measured channels
0 | missing values
Jan–May 2016 | 4.5 months
:::

:::glossarynote
:::

:::keyidea
Two of the 28 columns, `rv1` and `rv2`, are **random numbers the authors planted on
purpose** to test whether a model can identify a feature that carries no signal. We
come back to them at the end.
:::

## Why a linear model is not enough here

:::narration
Before reaching for a neural network, always check whether something simpler would
do. Run the first lab. It ranks every sensor by how strongly it correlates with
appliance load, and you will find that the strongest single relationship in the whole
dataset is about zero point two. That is very weak. No sensor moves reliably with
energy use. But weak linear correlation does not mean there is no signal. It means
the signal is not a straight line. It is in the combinations: kitchen temperature
rising at seven in the evening on a weekday means something quite different from the
same reading at three in the morning.
:::

:::pylab{title="Load the data and check the linear ceiling" packages="numpy,pandas,scikit-learn"}
# step: Load the measured data
import pandas as pd, numpy as np
from pyodide.http import open_url

URL = ("https://raw.githubusercontent.com/LuisM78/"
       "Appliances-energy-prediction-data/master/energydata_complete.csv")

df = pd.read_csv(open_url(URL), parse_dates=["date"]).sort_values("date")
df = df.iloc[::4].reset_index(drop=True)   # every 40 min, to keep the browser quick

print("rows, columns :", df.shape)
print("date range    :", df.date.min(), "->", df.date.max())
print("missing values:", int(df.isna().sum().sum()))

# step: How strong is the strongest single correlation?
corr = df.drop(columns=["date"]).corr()["Appliances"].drop("Appliances").abs()
print(corr.sort_values(ascending=False).head(8).round(3).to_string())
print("\nStrongest single correlation:", round(corr.max(), 3))
print("A linear model can only use relationships like these.")
:::

## Feature engineering: the clock

:::narration
Occupancy drives appliance use, and occupancy follows the clock, so we hand the model
the time of day. One detail matters. If you feed in the hour as a number from zero to
twenty three, the model thinks eleven p.m. and midnight are twenty three units apart,
when really they are adjacent. So we wrap the hour around a circle using sine and
cosine. That is the whole trick, and it is worth remembering for anything seasonal.
:::

:::pylab{title="Wrap the clock, then fit a baseline" packages="numpy,pandas,scikit-learn"}
# step: Cyclical time features
df["hour_sin"]   = np.sin(2*np.pi*df.date.dt.hour/24)
df["hour_cos"]   = np.cos(2*np.pi*df.date.dt.hour/24)
df["is_weekend"] = (df.date.dt.dayofweek >= 5).astype(int)

sensors  = [c for c in df.columns
            if c not in ["date","Appliances","hour_sin","hour_cos","is_weekend"]]
features = sensors + ["hour_sin","hour_cos","is_weekend"]
print(len(features), "input features")
print("note - the planted random columns are still in there:",
      [f for f in features if f.startswith("rv")])

# step: Linear baseline - never skip this
from sklearn.model_selection import train_test_split
from sklearn.linear_model import LinearRegression
from sklearn.metrics import r2_score, mean_absolute_error

X, y = df[features].values, df["Appliances"].values
X_tr, X_te, y_tr, y_te = train_test_split(X, y, test_size=0.2, random_state=498)

lin = LinearRegression().fit(X_tr, y_tr)
print(f"Linear regression   R2 = {r2_score(y_te, lin.predict(X_te)):.3f}")
print("If this had scored 0.9, the honest answer would be to use it and go home.")
:::

## Scaling is part of the model

:::narration
This is the step students skip most often and the one that costs the most. Our inputs
sit on wildly different scales: humidity from twenty to ninety percent, atmospheric
pressure around seven hundred and fifty millimetres of mercury. Gradient descent
applies one learning rate to every weight, so the large-valued features dominate the
step and the small ones barely move. The lab below trains the same network twice, once
scaled and once not. Everything else is identical, including the seed.
:::

:::figure{id=scaling caption="Figure 1. One learning rate is shared by every weight, so features on bigger scales dominate the step. Redrawn for this module."}
:::

:::pylab{title="The ablation: what standardisation is worth" packages="numpy,pandas,scikit-learn"}
# step: Train with and without scaling
from sklearn.preprocessing import StandardScaler
from sklearn.neural_network import MLPRegressor

def ann(seed=498):
    return MLPRegressor(hidden_layer_sizes=(128, 64), activation="relu",
                        learning_rate_init=1e-3, batch_size=128, max_iter=220,
                        early_stopping=True, n_iter_no_change=15,
                        validation_fraction=0.15, random_state=seed)

scaler = StandardScaler().fit(X_tr)        # fit on TRAIN only - never on the test set
Xs_tr, Xs_te = scaler.transform(X_tr), scaler.transform(X_te)

scaled = ann().fit(Xs_tr, y_tr)
raw    = ann().fit(X_tr,  y_tr)

print(f"ANN with scaling     R2 = {r2_score(y_te, scaled.predict(Xs_te)):6.3f}")
print(f"ANN without scaling  R2 = {r2_score(y_te, raw.predict(X_te)):6.3f}")
print("\nSame network. Same data. Same seed. Nothing errored, nothing warned you.")
:::

:::keyidea
Fit the scaler on the training set only, then apply those same statistics to
validation and test. Fitting on everything leaks information about the test set into
training and your score becomes fiction.
:::

## What the model is actually using

:::narration
Which inputs is the model relying on? Permutation importance answers this by
shuffling one column at a time and measuring how much the score falls. If shuffling a
column barely hurts, the model was not using it. And now the reveal. Remember r v one
and r v two? They are pure random numbers, planted by the people who published this
dataset. A trustworthy model should rank them near the bottom. Check where yours put
them. If a random column ever ranks near the top of your importance chart, stop, and
go and find what is broken in your pipeline.
:::

:::pylab{title="Permutation importance and the planted noise" packages="numpy,pandas,scikit-learn"}
# step: Shuffle one column at a time
base = r2_score(y_te, scaled.predict(Xs_te))
rng, drop = np.random.default_rng(498), {}
for i, name in enumerate(features):
    Xp = Xs_te.copy(); rng.shuffle(Xp[:, i])
    drop[name] = base - r2_score(y_te, scaled.predict(Xp))

s = pd.Series(drop).sort_values(ascending=False)
print("MOST relied on:\n" + s.head(6).round(4).to_string())
print("\nLEAST relied on:\n" + s.tail(6).round(4).to_string())
print("\nRank of the two planted random columns, out of", len(features), ":",
      [int(s.rank(ascending=False)[c]) for c in ["rv1", "rv2"]])
:::

## The honest test: split by time

:::narration
One last thing, and it is the most important idea in the episode. Our eighty twenty
split was random, but these rows are only ten minutes apart. Almost every row in the
test set has a nearly identical twin sitting in the training set. The model can score
well by half-remembering rather than by understanding. So here we split by time
instead: train on January through April, then predict May. The score collapses. That
is not a bug. That is the truth about how this model would perform if you deployed it
in the building tomorrow. When your data has a time dimension, and building data
almost always does, a random split will flatter you.
:::

:::pylab{title="Random split versus chronological split" packages="numpy,pandas,scikit-learn"}
# step: Train on Jan-Apr, predict May
cut = int(len(df) * 0.8)
Xtr2, Xte2 = df[features].values[:cut], df[features].values[cut:]
ytr2, yte2 = y[:cut], y[cut:]

sc2 = StandardScaler().fit(Xtr2)
m2  = ann().fit(sc2.transform(Xtr2), ytr2)

print(f"Random split        R2 = {base:6.3f}   <- what we reported above")
print(f"Chronological split R2 = {r2_score(yte2, m2.predict(sc2.transform(Xte2))):6.3f}"
      "   <- train Jan-Apr, predict May")
print("\nWhich number would you put in front of a building owner?")
:::

## What this episode establishes, and what it does not

:::narration
Finally, the boundary, because the course requires it and because a number without a
range is not a result. Everything here comes from a single occupied house near Mons
in Belgium, ten-minute readings across four and a half months from January to May.
One temperate maritime climate, one occupancy pattern, and no cooling season in that
window. A model fitted here does not transfer to another building, another climate,
or another year. State the range your own model was fitted on, every single time you
report a number from it.
:::

:::stats
1 house | occupied, low-energy, near Mons, Belgium
1 climate | temperate maritime, heating-dominated
0 | cooling seasons in the window
:::

- **Geometry range** — one dwelling; no variation in form, envelope, or orientation.
- **Climate range** — a single heating-dominated period, January to May.
- **Metrics** — R² and MAE on a held-out split. No uncertainty interval is reported.
- **Known failure conditions** — another building, another climate, another year, or
  a summer cooling load. A random split on ten-minute data also flatters the score,
  as the lab above measures.

:::keyidea
A network learns patterns in its training data. It does not establish causation,
guarantee code compliance, or replace a licensed professional's judgment.
:::
