## Central question

Images describe appearance. How can a model represent the *relationships* among
rooms, systems, buildings, or urban networks?

:::narration
A floor plan is not really a picture. It is a set of rooms and the relationships
between them: which room opens onto which, what you can see from where, where air and
people move. A graph stores exactly that — nodes for the things, edges for the
relationships — and a graph neural network learns on it by letting each node send
messages to its neighbours. One important warning before we go on. A graph is a way
of storing data. A G N N is a neural model that learns on that data. They are not the
same word, and the difference matters when you write it up. In this episode you will
build the adjacency matrix of a small plan, pass messages across it by hand, and see
what happens when you pass too many.
:::

:::figure{id=plan_to_graph caption="Figure 1. The same seven rooms as geometry and as relationships. Redrawn for this module."}
:::

:::flow
Rooms and doors > Nodes, edges, features > One layer: mix with neighbours > Two layers: neighbours of neighbours > Readout: a node, an edge, or the whole plan
:::

By the end of this episode you should be able to:

- Write a floor plan as an adjacency matrix and a feature table
- Explain one layer of message passing and what "two layers" reaches
- Say why a GNN's weights are shared and why its aggregation must ignore order
- Distinguish a graph, a hypergraph, and a GNN in one sentence each

## Graph representation

:::narration
A graph has nodes and edges, and both can carry features. For a building, the nodes
might be rooms, with area, program, occupancy and temperature attached. The edges
might be doors, adjacency, sightlines or airflow, with distance and connection type
attached. Global features describe the whole graph: site, climate, the project
target. The choice of what is a node and what is an edge is a modelling decision,
and it is yours. The same apartment could be a graph of rooms, a graph of walls, or
a graph of sensors, and each answers a different question.
:::

- **Node** — a room, facade, sensor, building, or urban block.
- **Edge** — adjacency, circulation, visibility, airflow, similarity, or energy
  exchange.
- **Node features** — area, program, occupancy, temperature, material.
- **Edge features** — distance, connection type, shared boundary, direction,
  capacity, flow.
- **Global features** — site, climate, project target, building-level properties.

:::cards
Node-level task | one answer per node | which rooms overheat; which sensors are faulty
Edge-level task | one answer per pair | should these two rooms be adjacent; will this door see traffic
Graph-level task | one answer per graph | does this plan meet the daylight target; predicted energy per plan
:::

:::technical{summary="The adjacency matrix, and why it is the whole representation"}
For n nodes, A is an n×n matrix with A[i, j] = 1 when i and j are connected (both
directions for an undirected graph). Node features form an n×d matrix X. Together A
and X are the graph. Two facts follow:

- Renumbering the rooms permutes the rows and columns of A and the rows of X but
  changes nothing about the plan. A model on graphs must give the same answer either
  way. That is why aggregation has to be a mean, sum or max: they do not care about
  order.
- A @ X gives every node the sum of its neighbours' features. That single matrix
  product is message passing. Everything else is normalisation and a learned weight
  matrix.
:::

## GNN message passing

:::narration
One layer of a graph neural network does three things. Each node collects messages
from its neighbours. It aggregates them with an operation that does not care about
order, usually a mean or a sum, because the rooms have no natural order. Then it
updates its own state with a small network that takes its old state and the
aggregate and produces a new one. That small network is the same for every node,
which is weight sharing again, exactly as in a C N N: a kernel shared across
positions there, a function shared across nodes here. Stack a second layer and each
node now knows about its neighbours' neighbours. Try the widget: start a signal in
one room and count the layers it takes to reach the far bedroom.
:::

:::figure{id=message_passing caption="Figure 2. One layer: messages in, aggregate, update. Redrawn for this module."}
:::

:::widget{id=message-lab}
:::

1. Each node begins with its own features.
2. The node receives messages from connected neighbours.
3. Neighbour messages are aggregated.
4. The node updates its representation.
5. Multiple layers allow information to travel farther through the graph.
6. The model predicts node labels, edge relationships, graph-level properties, or new
   structures.

:::keyidea
A graph is a data representation. A {{GNN}} is a neural model that learns on graphs.
A hypergraph model, an adjacency algorithm, or a self-organizing map is **not**
automatically a GNN. Use the word only when a neural message-passing model is
actually doing the learning.
:::

:::predict
In the widget, a signal starts in the kitchen. The kitchen has one door, to the
living room. How many layers does the signal need to reach Bed 1?
- One | One layer reaches only the living room, the kitchen's sole neighbour.
- Two | Two layers reach the hall, entry, and bed 2 — the living room's neighbours.
- *Three | Yes. Kitchen → Living → Hall → Bed 1 is three hops, so three layers.
:::

:::technical{summary="The graph convolution layer, in one line"}
The most common layer (Kipf & Welling, 2017) is

```
H_next = ReLU( D^-1/2 (A + I) D^-1/2  @  H  @  W )
```

A + I adds a self-loop so every node keeps its own state; D is the diagonal matrix of
node degrees, and the two D^−1/2 factors normalise so that well-connected nodes do not
dominate. H is the n×d feature matrix, W the d×d′ weight matrix shared by all nodes.
The lab uses the simpler row normalisation D^−1(A + I), which is a mean over self and
neighbours — the same thing the widget does.
:::

## Interactive code lab — message passing in numpy

:::narration
The lab writes the seven-room plan as a seven by seven adjacency matrix, builds the
mean-over-neighbours propagation matrix, and pushes a signal from the kitchen through
it one layer at a time. You watch the numbers spread. Then a two-layer graph
convolution with real node features, area and program and windows, and untrained
weights: the point is the shapes, and the readout that turns seven node vectors into
one vector for the whole plan. The last step applies twelve layers and watches every
room converge to the same value. That is over-smoothing, and it is why practical G N
Ns are shallow.
:::

:::pylab{title="Message passing on a seven-room plan" packages=numpy}
# step: A floor plan as an adjacency matrix
import numpy as np
rooms = ["Entry", "Living", "Kitchen", "Hall", "Bed 1", "Bath", "Bed 2"]
doors = [("Entry", "Living"), ("Entry", "Hall"), ("Living", "Kitchen"), ("Living", "Hall"),
         ("Hall", "Bed 1"), ("Hall", "Bath"), ("Living", "Bed 2"), ("Bath", "Bed 2")]

n = len(rooms)
A = np.zeros((n, n))
for a, b in doors:
    i, j = rooms.index(a), rooms.index(b)
    A[i, j] = A[j, i] = 1                 # undirected: a door works both ways
print("adjacency matrix A (1 = connected by a door)\n")
print("         " + " ".join(f"{r[:5]:>5}" for r in rooms))
for r, row in zip(rooms, A):
    print(f"{r:8s} " + " ".join(f"{int(v):>5}" for v in row))
print("\ndegree (number of doors):", {r: int(d) for r, d in zip(rooms, A.sum(1))})

# step: One layer of message passing, by hand
A_hat = A + np.eye(n)                     # every node also listens to itself
D_inv = np.diag(1 / A_hat.sum(1))         # 1 / (number of neighbours + 1)
P = D_inv @ A_hat                         # P @ h  =  mean of self and neighbours

h = np.zeros(n); h[rooms.index("Kitchen")] = 1.0     # a signal that starts in the kitchen
print("signal strength after each layer (starts in the kitchen):")
print(f"{'layer':>5}  " + "  ".join(f"{r[:5]:>5}" for r in rooms))
for layer in range(5):
    print(f"{layer:>5}  " + "  ".join(f"{v:5.2f}" for v in h))
    h = P @ h
print("\nLayer 1 reaches the living room. Layer 2 reaches the hall, entry and bed 2. Layer 3 reaches everything.")

# step: A two-layer GCN forward pass with real node features
features = np.array([              # area (m2), is a bedroom, has an exterior window
    [8, 0, 1], [32, 0, 1], [14, 0, 1], [6, 0, 0], [16, 1, 1], [5, 0, 0], [18, 1, 1]], dtype=float)
X = (features - features.mean(0)) / (features.std(0) + 1e-9)     # standardise columns

rng = np.random.default_rng(0)
W1, W2 = rng.normal(0, 0.5, (3, 4)), rng.normal(0, 0.5, (4, 2))  # untrained weights, shared by every node
relu = lambda z: np.maximum(0, z)

H1 = relu(P @ X @ W1)        # layer 1: mix neighbours, then transform   (7 x 4)
H2 = P @ H1 @ W2             # layer 2: mix again                          (7 x 2)
print("node embeddings after two layers (untrained - the shape matters, not the numbers):")
for r, e in zip(rooms, H2):
    print(f"{r:8s} {e.round(2)}")

graph_vector = H2.mean(0)    # readout: one vector for the whole plan
print("\ngraph-level readout:", graph_vector.round(3), "- this is what a plan-level predictor would consume")
print("Training = adjusting W1 and W2 so these embeddings predict a label. Same weights at every room.")

# step: Over-smoothing - what many layers do
h = X[:, 0].copy()           # start from the (standardised) room areas
for layer in range(12):
    if layer in (0, 1, 2, 4, 8, 11):
        print(f"after {layer:2d} layers  spread between rooms = {h.max() - h.min():.3f}")
    h = P @ h
print("\nWith mean aggregation every node converges to the same value. Two or three layers is usually enough.")
:::

:::keyidea
**Over-smoothing.** Every layer averages a node with its neighbours. After enough
layers every node holds the same average and the model can no longer tell rooms
apart. Real GNNs are two to four layers deep, with skip connections when they need
more.
:::

## Architectural applications

:::narration
Where graphs earn their place. Adjacency and circulation reasoning, where the
question is literally about connections. Floor-plan analysis and generation. Building
systems and energy networks, where pipes and ducts are edges. Urban accessibility and
mobility. Mesh-based physics, where a simulation mesh is a graph of cells and a G N N
can learn to step it forward. And knowledge graphs that link buildings, materials,
performance and regulation. The common thread is that the relationships are the
data. If your data is a table of independent rows, you do not need a graph, and
using one adds nothing but complexity.
:::

- Room adjacency and circulation reasoning.
- Floor-plan analysis or generation.
- Building-system and energy-network modeling.
- Urban accessibility and mobility relationships.
- Mesh-based physical-field approximation.
- Knowledge graphs linking buildings, materials, performance, and regulations.

:::compare
Grid (CNN) | pixels with a fixed neighbourhood | Right for images and rasters. Wrong for a plan, where "next to" is not a pixel offset and rooms have different numbers of neighbours.
Graph (GNN) | nodes with whatever neighbours they have | Right for plans, networks, and meshes. Costs you the modelling decision of what a node and an edge are.
:::

## Hypergraph distinction

:::narration
A normal edge connects two nodes. A hyperedge connects any number at once, which
lets one apartment, one circulation zone, or one functional group be a single object
rather than a clique of pairwise links. That is a richer representation. It is still
a representation. Whether a neural model learns on it is a separate question, and
the answer in many published pipelines is no: the hypergraph feeds rules or an
optimiser, not a network. Be precise about which you did.
:::

- A normal graph edge usually connects two nodes.
- A hyperedge can connect several nodes simultaneously.
- A hyperedge can represent one apartment, a shared circulation zone, a functional
  group, or a multi-room relationship.

:::flow
Program requirements > room nodes > adjacency and access edges > graph or hypergraph > optional GNN > geometry-generation rules > candidate floor plans > daylight, carbon, circulation and space-efficiency evaluation > designer selection
:::

## Research example

:::narration
An example of the pipeline in use. Weber, Mueller and Reinhart encode floor-plan
organisation as a hypergraph and use it to generate geometry automatically, then
evaluate the results. Within that study, improving space efficiency outperformed
envelope upgrades for operational carbon in seventy-two percent of surveyed Zurich
buildings, sixty-one percent in New York and thirty-three percent in Singapore, and a
Zurich case study raised daylight access by up to twenty-four percent. Those numbers
belong to that study's datasets and assumptions. Quote them with the scope attached,
or not at all.
:::

Weber, Mueller and Reinhart use a hypergraph to encode floor-plan organization and
support automatic geometry generation. Within that study, improved space efficiency
outperformed envelope upgrades for operational carbon in **72%** of surveyed Zurich
buildings, **61%** in New York, and **33%** in Singapore. A Zurich case study

:::boundary
Data | a seven-room plan written by hand for the lab; the research figures are [[retrieved]] from the cited study and scoped to its datasets
Evidence | lab outputs are [[simulated]] with untrained weights; they show shapes and mechanics, not a prediction
Establishes | what a graph stores, what one message-passing layer computes, why weights are shared and aggregation is order-free, why depth is limited
Does not establish | that a GNN outperforms a simpler model on any plan dataset — that comparison has to be run, against a baseline, on a grouped split
:::

:::reflect
A paper builds a hypergraph of room relationships, runs a rule-based generator on
it, and describes the method as "a GNN approach". Is the description accurate?
- Yes — a hypergraph is a kind of graph | The data structure is graph-like. Nothing neural learned on it.
- *No — no neural message-passing model learned anything; it is a graph-based method | Yes. "GNN" names a model that learns on graphs, not the presence of a graph.
- Yes, if the rules were tuned by hand | Tuning rules is not training a network.
:::
